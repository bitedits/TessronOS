# 第9章　ネットワークとカレンダ

## 9.1 TCP/IP

TCP/IPスタックはNetBSD 11.0のカーネルのものである。NetBSDのカーネルのコードを、ハイパーコールと呼ぶ小さなインタフェースの上で動く部品として切り出したrumpカーネルの仕組みを使い、TessronOSのカーネルの中で動かす。ソースコードはNetBSDの配布物をそのまま使い、変更しない。`tools/netbsd/build.sh`がソースを取得してTessronOSのツールチェーンでコンパイルし、1つのオブジェクト(`~/tessronos-netbsd/rumpnet.o`)にまとめ、カーネルにリンクする(12.2)。

対応しているのは、IPv4、IPv6、TCP、UDP、ICMP、ICMPv6、ARP、近隣探索、IGMPとMLDによるマルチキャスト、Ethernetとループバックである。TCPはウインドウスケール、SACK、タイムスタンプを持ち、輻輳制御はNewRenoである。IPv6のアドレスは、スタックが付けるリンクローカルアドレスと、ルータ広告から作るアドレス(SLAAC)である。DHCP、ルータ広告の処理、DNSによる名前解決、SNTPは、NetBSDでもカーネルの外のプログラムが行うものなので、スタックの外にあるTessronOSのコードで行う(9.3、9.4)。

以前のスタックであるlwIP 2.2.0も残してあり、`make NETSTACK=lwip`でビルドすると、NetBSDのスタックの代わりに組み込まれる。どちらのスタックでも、`so_`の関数の名前、引数、定数、構造体、エラーコード、SVCクラス5の番号は同じである。

### 9.1.1 構成

| 部分 | 場所 | 内容 |

### 9.1.2 ハイパーコール

rumpカーネルは、ホストに対してハイパーコール(`rumpuser_`で始まる関数、インタフェースの版は17)を呼ぶ。TessronOSでは、ホストはカーネル自身である。

| 資源 | 実現 |
| --- | --- |
| メモリ | 2のべき乗のページ数の要求はページアロケータから、それ以外は`Kmalloc`から確保する。1ページの要求は、一度確保したページをrumpカーネル専用のリストで使い回し、ページアロケータには返さない。起動時に4MB分を確保しておく。rumpカーネルが使うメモリの上限は128MBで、それを超えるとrumpカーネル自身がプールを縮める |
| スレッド | T-Kernelのタスク。優先度10、スタック64KB |
| 仮想プロセッサ | 1つだけ持つ。rumpカーネルのスレッドは仮想プロセッサを持っている間だけrumpカーネルのコードを実行する。プロセッサの数と同じだけ持たせると、Raspberry Pi 5の4つのコアでページの多数の取得が重なったときに、スレッドのロックと載っている仮想プロセッサの対応が食い違い、rumpカーネルのスケジューラの検査で止まったため、1つにした。呼び出す側のタスクはrumpカーネルの外では並行に動く |
| ミューテックス、読み書きロック、条件変数 | スピンロックで守る待ちの列と、待つ間だけ借りるセマフォで作る。rumpカーネルは数千のロックを作るので、T-Kernelのオブジェクトは使わない。ロックを解放すると待っているタスクを起こし、起きたタスクがあらためてロックを取る。優先度の低いタスクがロックを渡されたまま実行されない、ということが起きない。スピンミューテックスは、仮想プロセッサを持ったまま取りに行くロックである。そのため、スピンミューテックスで条件変数を待っていたスレッドは、起きたら先に仮想プロセッサを取り戻し、それからミューテックスを取る。逆の順では、ミューテックスを持って仮想プロセッサを待つスレッドと、仮想プロセッサを持ってミューテックスを待つスレッドが互いを待ち、仮想プロセッサが1つなのでrumpカーネル全体が止まる(`select`と`poll`の待ちで起きた) |
| 時計 | システム時刻と単調時刻(`ts_get_mono`)。rumpカーネルのタイマは1秒に100回の刻みで進むので、その時計のスレッドは10ミリ秒ごとに起きる(4.4) |
| 乱数 | カーネルの乱数(`ts_get_random`) |
| コンソール | T-Monitorのコンソールに1行ずつ出力する |

rumpカーネルの外で待つとき(カードの読み書き、ロックの待ち、時計による待ち)は、仮想プロセッサとビッグロックを手放してから待ち、終わると取り直す。こうしないと、待っている間、rumpカーネルのほかのスレッドが動けない。

rumpカーネルは、どのスレッドとして動いているかを、タスクIDで引く表で知る。`so_`を呼んだタスクには、ソケットを持つrumpカーネルのプロセスのスレッドを1つ貸し、呼出しが終わると返してもらう。スレッドは必要な数だけ作り、以後は使い回す。

`make RUTRACE=1`でビルドすると、ロックを5秒以上待っているタスクを、待たせた場所のアドレスとともにコンソールに出力する。ロックの取り合いで止まったときの調査に使う。

ロックと条件変数の待ちは、セマフォの時間の指定のない待ちが合図でだけ終わることを前提にしている。カーネルが別のCPUの合図と食い違って`E_TMOUT`を返すと(4.3)、ロックの待ちは合図が来たものとして進むが、条件変数の時間切れの扱いでは、もう取られた合図を待ち続けてそのスレッドが止まり、カーネルが後から書くエラーコードがスレッドのスタックを壊す。ブラウザの試験の切り替わりで、ワークキューのスレッドが仮想プロセッサを待つ`rump_schedule_cpu_interlock`の中で、上位が欠けた戻りアドレスへ戻って止まったのはこのためで、4.3の直しで起きなくなった。

試験グループ`rump`(`tests/ktest/ktest_rump.c`)は、4つのCPUからrumpカーネルに同時に負荷を掛ける。優先度の違う多くのタスクが、ループバックで接続を作っては使って閉じ(1つの待ち受けのソケットを3つのサーバが受け付けて返す)、データグラムを1〜2ミリ秒の待ちでやりとりし、何も来ないソケットを1ミリ秒ずつ待ち、ソケットを作ってはすぐ閉じる。あわせて、プロセスが接続して1バイト送り、返事を受けて自分で終わるか、返事のないまま待っているところを終了させられる。合図で終わる待ちと時間切れになる待ちが、rumpカーネルのロックと条件変数の中で交差する。すべてが進み、止めればすべてが終わり、その後も接続が通ることを確かめる。時間は`make KT_RUMP_S=<秒>`で変える(既定は20秒)。`STKWATCH=1`(4.7.6)と合わせると、スタックの書き換えを起きたところで検出する。

### 9.1.3 インタフェース

ネットワークデバイスはデバイス`neta`で、スタックはドライバを直接呼ばずにこのインタフェースを使う。Raspberry Pi 5ではRP1のEthernet、QEMUではvirtio-netがその下にある。

RP1のEthernet(Cadence GEM、`device/net/eth_rp1.c`)は割込みを使わず、読み手が受信のリングを見る。受信の記述子は128個で、1つが16バイトなので、データキャッシュの1ライン(64バイト)に4つが入る。1つの記述子をキャッシュから書き戻すと、同じラインのほかの3つもキャッシュにあった古い値で書き戻される。その間にコントローラが埋めた記述子は空きに戻ってフレームが失われ、ドライバはコントローラが追い越した記述子を待ち続けることになる。そこで、受信の記述子は同じラインの4つを読み終えてからまとめてコントローラに返し、コントローラが書く可能性のあるラインには書き込まない。リングが満ちて受信できなかったフレーム(`RSR`のBNA)は捨てられ、コントローラは記述子が返されると受信を続ける。返した後も200ミリ秒フレームが入らないときだけ、受信を止め、1ミリ秒置いてからリング全体を先頭から返し直して再開する(`eth: receiving started again`)。

rumpカーネルの中では、カードは`neta0`、ループバックは`lo0`(127.0.0.1)というインタフェースになる。`neta0`が送るフレームは、リングに入れて専用のタスクがデバイスに書き込む。デバイスはフレームを受け取るまで書いたタスクを待たせるので、rumpカーネルのスレッドが自分で書くと、フレームごとにスタック全体が止まるからである。受信は`neta0`のスレッドがデバイスを読んで待ち、フレームが届くと、そのときまでに届いていたものと合わせて最大16個をまとめてスタックに渡す。リンクの状態は「不明」とし、スタックはこれを接続されているものとして扱う。

### 9.1.4 性能

QEMU(Windows版、4コア)での測定値を示す。`ktest_so`と`ktest_svcio`(`NET=user`)が16MBを送って測る。

| 項目 | NetBSD | lwIP |
| --- | --- | --- |
| ループバックのTCP | 48〜66MB/秒 | 31〜33MB/秒 |
| ホストからのTCP | 10〜16MB/秒 | 13.5〜14MB/秒 |
| ホストへのTCP | 3〜5MB/秒 | 10〜11MB/秒 |
| 何もしない呼出し(`so_fcntl`)1回 | 1.5〜6マイクロ秒 | 0.05マイクロ秒 |

ホストへの送信が遅いのは、QEMUのユーザモードネットワークが受け取ったセグメントごとにACKを返し、ACKのたびに受信、プロトコル処理、送信のタスクが順に動くためである。1回の呼出しは、rumpカーネルのスレッドとして仮想プロセッサを取り、NetBSDのシステムコールとしてディスクリプタを引くので、関数を直接呼ぶlwIPより時間がかかる。

## 9.2 ソケット

T2EXのBSDソケット互換の関数`so_`を提供する。カーネル内からは下表のすべてを関数として呼べる。プロセスからはSVCクラス5で、「ソケット」の行のすべて、`so_send`、`so_recv`、`so_sendto`、`so_recvfrom`、`so_recvtos`、`so_poll`、`so_getsockopt`、`so_setsockopt`、`so_fcntl`、`so_resolve`、`so_resolveall`、「インタフェース」の行の`so_getifaddr`、`so_getdns`、`so_setifaddr`、`so_dhcp_start`、`so_getobj`を呼べる。名前と引数はどちらも同じである。

| 分類 | 関数 |
| --- | --- |
| ソケット | `so_socket`、`so_close`、`so_bind`、`so_connect`、`so_listen`、`so_accept`、`so_shutdown`、`so_getsockname`、`so_getpeername` |
| 送受信 | `so_send`、`so_recv`、`so_sendto`、`so_recvfrom`、`so_recvtos`、`so_read`、`so_write`、`so_sendmsg`、`so_recvmsg` |
| 待ち合わせ | `so_select`(カーネル)、`so_poll`(プロセス) |
| オプション | `so_getsockopt`、`so_setsockopt`、`so_ioctl`、`so_fcntl` |
| 名前解決 | `so_getaddrinfo`、`so_resolve`、`so_resolveall`、`so_getnameinfo`、`so_gethostname`、`so_sethostname` |
| インタフェース | `so_getifaddr`、`so_getdns`、`so_setifaddr`、`so_dhcp_start`、`so_getifaddr6`、`so_getdns6`、`so_setip6`、`so_getip6`、`so_setdns6` |
| 実身 | `so_getobj` |

IPv6のアドレスの状態を読む関数(`so_getifaddr6`、`so_getdns6`、`so_getip6`)と、IPv6の設定を変える関数(`so_setip6`、`so_setdns6`)はSVCにしていない。プロセスはIPv6の状態をシステムの実身のレコード7で読み(9.3.4、8.4)、設定はネットワーク設定の実身を書き換えて変える(9.3)。デバイスやソケットと同じく、資源の状態は実身のレコードとして見せ、APIを増やさない方針による。

ソケットは作成したプロセスが所有し、プロセスが終了すると閉じられる。他のプロセスのソケット番号は使えない。インタフェースのアドレスを変更する関数と`so_dhcp_start`は管理者だけが呼べる。

構造体と定数は`include/ts/sodef.h`(プロセスには`include/ts/soapp.h`)にある。アドレスの構造体はファミリの前に長さのバイトを持つ。値はlwIPのときと同じで、`so_`の層がNetBSDの値との間で変換する。ソケット番号はシステム全体で0から63(`SO_MAX`)で、1つの番号はrumpカーネルの1つのディスクリプタに対応する。すべてのソケットは、rumpカーネルの1つのプロセスのディスクリプタである。

ソケットはIPv4(`AF_INET`、`struct sockaddr_in`)でもIPv6(`AF_INET6`、`struct sockaddr_in6`)でも作れ、`so_bind`、`so_connect`、`so_accept`、`so_getsockname`、`so_getpeername`、`so_sendto`、`so_recvfrom`はどちらのアドレスも受け渡す。リンクローカルアドレスは、`sin6_scope_id`にインタフェースの番号(`so_ifnametoindex`)を入れて指す。`IPV6_V6ONLY`の既定はNetBSDと同じく1で、IPv6のソケットはIPv6だけを扱う。0にしてから`::`にバインドしたソケットはIPv4の接続も受け、相手のアドレスは`::ffff:a.b.c.d`になる。`IPV6_V6ONLY`はバインドする前にだけ変えられる。ほかに`IPV6_UNICAST_HOPS`、`IPV6_MULTICAST_IF`、`IPV6_MULTICAST_HOPS`、`IPV6_MULTICAST_LOOP`、`IPV6_JOIN_GROUP`、`IPV6_LEAVE_GROUP`を扱う。

送るデータグラムのTOS(IPv4、`IP_TOS`)とトラフィッククラス(IPv6、`IPV6_TCLASS`)は設定でき、読み出せる。下位の2ビットはECNのビットである。受け取ったデータグラムのTOSとトラフィッククラスは、ソケットが`IP_RECVTOS`か`IPV6_RECVTCLASS`を1にしておくと、`so_recvtos`(`so_recvfrom`と同じ引数に、値を受け取る`INT *p_tos`を加えたもの)が返す。求めていないソケットと、値が来なかったデータグラムでは-1になる。IPv6の値はNetBSDの付随データ(`IPV6_TCLASS`)がそのまま運ぶ。IPv4には、NetBSDに受け取ったTOSを渡すオプションがない。そこで`IP_RECVTOS`はNetBSDの`IP_RECVTTL`として設定し、TessronOSの部品(`tsnet_conf.c`)が、受信の付随データを作るNetBSDの関数`ip_savecontrol`の後で、TTLの横にTOSの1バイトを足す。NetBSDのソースは変えず、リンクのときにその関数の呼出しを部品の関数に向ける(`ld --wrap`、12.7)。TTLの付随データは渡さない。lwIPのときは、`so_recvtos`はいつも-1を返す。

プロセスのPOSIXのソケット(`lib/libcxxrt/ts_socket.c`)も、Linuxの形の`AF_INET6`のソケットとアドレスを`so_`の形に変えて扱う。`IPV6_V6ONLY`、`SO_LINGER`、`IP_TOS`、`IPV6_TCLASS`、`IP_RECVTOS`、`IPV6_RECVTCLASS`を渡す。`recvmsg`は、付随データの場所があれば`so_recvtos`で受け取り、TOSを`IP_TOS`の1バイトの、トラフィッククラスを`IPV6_TCLASS`の`int`の付随データとして返す。`inet_pton`、`inet_ntop`、`getaddrinfo`、`getnameinfo`はIPv6のアドレスも扱う(9.3.2)。`poll`は1回に64まで(システムのソケットの数と同じ)のソケットを待てる。

エラーは、NetBSDのerrnoの値を次の表のエラーコードにして返す。表にないものは`E_SYS`である。`SO_ERROR`で読むerrnoの値も`sodef.h`の値にする。

| errno | エラーコード |
| --- | --- |
| `EINVAL`、`EFAULT` | `E_PAR` |
| `EBADF`、`ENOTSOCK` | `E_ID` |
| `EACCES` | `E_OACV` |
| `ENOMEM`、`ENOBUFS` | `E_NOMEM` |
| `EMFILE` | `E_LIMIT` |
| `EAGAIN`、`ETIMEDOUT` | `E_TMOUT`(ブロックしないソケットで待つことになった場合と、`SO_RCVTIMEO`などの時間切れ) |
| `EINPROGRESS`、`EALREADY`、`EADDRINUSE` | `E_BUSY` |
| `EISCONN`、`ENOTCONN` | `E_OBJ` |
| `ECONNRESET`、`ECONNABORTED`、`ECONNREFUSED`、`EHOSTUNREACH`、`ENETUNREACH`、`ENETDOWN`、`EHOSTDOWN`、`EPIPE` | `E_IO` |
| `EOPNOTSUPP`、`EAFNOSUPPORT`、`EPROTONOSUPPORT` | `E_NOSPT` |

NetBSDのソケットの動作のうち、以前と異なるものは`so_`の層で次のように合わせている。

- 接続が切れたソケットに書いてもシグナルは生じず、`E_IO`になる。
- `so_listen`のbacklogは指定にかかわらず最大値にする。受け付け待ちの接続の数は、以前から制限していない。
- データグラムのソケットの`SO_REUSEADDR`は、両方が指定していれば同じポートを共有できる。NetBSDではそのために`SO_REUSEPORT`も設定する。
- `FIONREAD`はデータのバイト数だけを返す。データグラムの送信元のアドレスは数えない。
- `so_fcntl`の`F_GETFL`は`O_NONBLOCK`と`O_RDWR`を返し、`F_SETFL`は`O_NONBLOCK`だけを受け付ける。
- `so_recvmsg`と`so_sendmsg`は補助データを扱わない。
- 64のソケット番号がすべて使われているときの`so_socket`と`so_accept`は、`E_LIMIT`を返す(lwIPでは`E_SYS`だった)。
- NetBSDでは受け付けたソケットが待ち受けのソケットの`O_NONBLOCK`を引き継ぐ。プロセスの`so_accept`は受け付ける間だけ待ち受けのソケットを`O_NONBLOCK`にするので、受け付けたソケットのフラグを待ち受けのソケットの元のフラグに戻す。

下位のスタックが持たない機能、たとえば帯域外データ(`so_sockatmark`)は、無期限に待つことがないよう`E_NOSPT`を返す。`so_resctl`と`so_break`も`E_NOSPT`である。

### 9.2.1 ソケットの実身

ソケットは通信の実身(`OB_T_CHANNEL`、サブタイプ`OB_S_SOCKET`)でもある(8.5)。`so_socket`と`so_accept`がソケット番号を割り当てたところで実身を作り、`so_close`が番号を返す前に消す。プロセスの終了による後始末(`knl_so_prc_end`)も`so_close`を通るので、同じように消える。スタックが実身の層を呼ぶのはこの2か所だけで、送受信やオプションの呼出しはこれまでどおり番号でソケットを指し、実身を探さない。番号のAPI(`so_`)もPOSIXのAPI(`lib/libcxxrt/ts_socket.c`)も変わらない。どちらのスタックでも同じ作りで、実身を扱うのはスタックの外の`obsock.c`である。

プロセスは`so_getobj`で自分のソケットの実身のUUIDを得て、`ob_opn_obj`で開ける。他のプロセスのソケット番号には`E_ID`を返す。実身は`ob_lst_obj(OB_T_CHANNEL, OB_S_SOCKET, ...)`でも列挙でき、プロセスの実身のレコード0からも仮身で辿れる。

| 項目 | 内容 |
| --- | --- |
| 名前 | `socket 3 (process 12)`。カーネルのソケットは`socket 3 (kernel)` |
| 保護 | 所有者は作ったプロセスが代理するユーザ、グループはその最初のグループ、モードは`rw-------`。変更はできない。カーネルのソケットの所有者はシステムである |
| レコード0 | 説明のxmlTAD。プロトコル、種類、両端のアドレスとポート、状態と、所有するプロセスの実身への仮身 |
| レコード1 | データ。読むと受信し、書くと送信する。大きさは受信して読んでいないバイト数 |
| メタデータ | `socket`の下に`number`、`process`(カーネルは0)、`family`(`inet`、`inet6`)、`type`(`stream`、`datagram`、`raw`)、`protocol`(`tcp`、`udp`など)、`local`と`remote`(`address`と`port`、ないときは`null`)、`state`(`listening`、`connected`、`bound`、`open`)、`waiting` |
| 削除 | `ob_del_obj`はソケットを閉じる |
| イベント | 閉じると`OB_E_DELETE`を1回通知する |

データをどのレコードに置くかは、通信の実身であるメッセージキューに合わせて決めた。キューではレコード0の書込みが送信、読出しが受信で、キーを`OB_O_NOWAIT`で開いていなければ、空のときと満杯のときに待つ。ソケットの実身はデバイスの実身と同じくレコード0を説明に使うので、データをレコード1に置き、送受信と待ち方をキューと同じにした。プロセスの呼出しは200ミリ秒ごとに区切って待ち、その間にプロセスが終了させられれば`E_DISWAI`で戻る(`so_recv`、`so_send`と同じ)。`OB_O_NOWAIT`のキーでは待たずに`E_TMOUT`を返す。ソケットに設定した`SO_RCVTIMEO`、`SO_SNDTIMEO`、`O_NONBLOCK`はそのまま効く。オフセットは0だけを受け付け、レコード0への書込みは`E_RONLY`である。

実身を作るにはUUIDが要る。実身の層が動き出す前(起動中の`so_main`)に作られたソケットは、実身の層が動き出したときに実身を与える。時計が設定される前に作られたソケットの実身は、version 4のUUIDで識別する(7.3)。

## 9.3 設定

ネットワーク設定は、ネットワーク設定の実身のレコード1にある次の形式の行である。キーと値の間はタブで区切る。

```text
$$HOST <ホスト名> cnet <サブネットマスク> <IPアドレス> NETDRV DEVICE=neta
$$DNS <名前> cnet <サブネットマスク> <IPアドレス> DOMAIN=<ドメイン>
$$DNS <名前> cnet <サブネットマスク> <IPアドレス>
$$GW gateway cnet <サブネットマスク> <IPアドレス>
$$NTP <NTPサーバ>
$$IPV6 <on|off> <auto|fixed|none> [temp]
$$IPV6ADDR <IPv6アドレス>/<プレフィックス長>
$$IPV6GW <IPv6アドレス>
$$IPV6DNS <IPv6アドレス>
$$IPV6DNS <IPv6アドレス>
```

自ホストのIPアドレスが0.0.0.0ならDHCPでアドレスを取得する。DNSサーバのアドレスが0.0.0.0ならDHCPで取得したものを使う。`$$GW`と`$$NTP`がキーだけの行なら、ゲートウェイを使わず、時刻合わせもしない。

`$$IPV6`はIPv6を使うかどうか(`on`、`off`)と、アドレスの決め方である。`auto`はルータ広告からアドレスを作り(9.3.3)、`temp`を付けると一時アドレスも作る。`fixed`は`$$IPV6ADDR`のアドレスとプレフィックス長をインタフェースに付け、`$$IPV6GW`をデフォルトルータにする。`none`はリンクローカルアドレスだけを使い、ほかのアドレスを付けない。`$$IPV6DNS`は2つまでのIPv6のDNSサーバで、ルータが示したものより先に尋ねる。アドレスの行がキーだけなら、そのアドレスはない。`$$IPV6`の行がない設定は`on auto`として扱う。アドレスはRFC 5952の最も短い形で書く(`lib/libconf`の`cf_ip6str`)。

デスクトップ構成では、起動時にこのレコードを読み込んで設定を反映する。以後は監視タスクがレコードの変更をイベントで受け取り、書き換えられるたびに、ホスト名とドメイン、インタフェースのアドレスとDNS、NTPサーバを順に設定し直す(`so_conf`)。ネットワーク設定の小物(第11章)はこのレコードを書き換えるだけである。

起動直後にDHCPでアドレスを取得するかどうかと、SNTPで時刻を合わせるかどうかは、`config.h`の`CNF_NET_DHCP`と`CNF_NET_SNTP`で決まる。Raspberry Pi 5の構成ではどちらも1で、起動するとアドレスを取得し、アドレスが決まったら時刻を合わせる。ルータ広告からIPv6のアドレスを作るかどうかは`CNF_NET_SLAAC`で決まり、どの構成でも1である(9.3.3)。起動後にネットワーク設定の実身を読むと、`$$IPV6`の行に従ってIPv6の設定を変える(9.3.4)。

固定のアドレスを設定すると(`so_setifaddr`)、アドレスとサブネットマスクから決まるブロードキャストアドレスとともに`neta0`に設定し、ゲートウェイをデフォルトの経路にする。

### 9.3.1 DHCP

DHCPのクライアント(`so_dhcp.c`)は専用のタスクで動き、スタックのUDPのソケットで問い合わせる。アドレスがまだないときは、インタフェースのアドレスを0.0.0.0、ブロードキャストアドレスを255.255.255.255にしておく。こうするとスタックは68番のポートからブロードキャストを送り、応答を受け取れる。サーバには応答をブロードキャストで返すよう求める。

DISCOVER、OFFER、REQUEST、ACKの順に進み、アドレス、サブネットマスク、ルータ、2つまでのDNSサーバを設定する。リース期間の半分で同じサーバに更新を求め、8分の7を過ぎたらどのサーバにでも求める。リースが切れるとアドレスを外して最初からやり直し、NAKを受け取ったときもやり直す。`so_dhcp_start`は最初から問い合わせ直すが、インタフェースにアドレスがあれば、新しいリースを得るまでそのアドレスを使い続ける。固定のアドレスを設定すると問い合わせをやめる。応答がなくてもエラーにはせず、間隔を4秒から64秒まで延ばしながら問い合わせを続ける。

### 9.3.2 名前解決

名前解決(`so_dns.c`)は、名前のIPv4アドレス(Aレコード)、IPv6アドレス(AAAAレコード)、またはその両方をDNSサーバに尋ねる。両方を尋ねるときは2つの問い合わせを同じサーバに続けて送り、2つの応答をまとめて待つ。一方の応答が来たら、もう一方は0.5秒だけ待つ。AAAAに答えないサーバのために名前解決のたびに待たされないよう、どちらかの種類のアドレスが得られたら、それ以上は尋ねない。CNAMEで別名が返っても、同じ応答に含まれるアドレスを使う。問い合わせるサーバは、IPv4のサーバとして設定で指定したもの、なければDHCPで得たもの(固定のアドレスなら`so_setifaddr`で指定したもの)、その後にルータ広告が示したIPv6のサーバ(9.3.3)で、それぞれのアドレスのファミリのUDPで尋ねる。サーバごとに、1秒、2秒、4秒、8秒と待ち時間を延ばしながら4回まで尋ねる。

答えは名前と種類(AとAAAA)ごとに、そのレコードが示す有効期間(最長5分)の間、64件まで保持する。存在しない名前と、その種類のアドレスを持たない名前は30秒保持する。ページが同じホストの名前を何度も解決しても、問い合わせは1回で済む。`localhost`は常に127.0.0.1と::1である。ドットを含まない名前が見つからなければ、設定のドメインを付けてもう一度尋ねる。

`so_resolveall`は名前のアドレスを、ファミリ(`AF_INET`、`AF_INET6`、両方なら`AF_UNSPEC`)を指定して最大16個返す(アドレスの構造体`T_SOADDR`はファミリ、リンクローカルアドレスのインタフェースの番号、16バイトのアドレス)。数字のアドレス(`2001:db8::1`、`fe80::1%neta0`、`10.0.2.2`)はそれ自体を返す。返す順は試すべき順で、RFC 6724の宛先アドレスの選択を簡略にしたものである。このホストが送信元に使えるアドレスを持たない宛先を後ろに回し、送信元と宛先のスコープが同じもの、方針表のラベルが同じものを先にし、残りを方針表の優先度の高い順にする。このため、IPv6のアドレスがリンクローカルかサイトローカル(QEMUのユーザモードネットワークが配るfec0::/64)だけのホストでは、IPv4のアドレスを先に試す。`SO_RA_ADDRCONFIG`を指定すると、外へ届くアドレス(IPv4のアドレス、またはリンクローカルでもサイトローカルでもないIPv6のアドレス)を持たないファミリは尋ねない。どちらのファミリのアドレスもまだないときは、この指定を無視する。ループバックのアドレスは外さない。

`so_getaddrinfo`は`so_resolveall`の答えを`struct addrinfo`の連結リストにして返す。`hints`の`AI_ADDRCONFIG`は`SO_RA_ADDRCONFIG`になり、`AI_NUMERICHOST`は数字のアドレスだけを受け付ける。名前を指定しないときは、ループバック(`AI_PASSIVE`なら任意)のIPv4とIPv6のアドレスを、IPv4を先にして返す。サービスは数字で指定する。`so_resolve`は従来どおり最初のIPv4アドレスを1つ返す。`so_getnameinfo`は数字だけを返し、IPv6のアドレスは最も短い形(RFC 5952)にし、リンクローカルアドレスには`%`とインタフェースの名前を付ける。

プロセスの`getaddrinfo`(`lib/libcxxrt/ts_socket.c`)は、数字のアドレスを自分で読み、名前はSVCの`so_resolveall`で尋ねて、その順のまま`struct addrinfo`のリストにする。`AI_ADDRCONFIG`、`AI_NUMERICHOST`、`AI_PASSIVE`、`AI_CANONNAME`を扱う。名前を指定しないときの答えはカーネルの`so_getaddrinfo`と同じである。`gethostbyname`は従来どおり最初のIPv4アドレスを返す。

### 9.3.3 IPv6のアドレスの自動設定

NetBSDのカーネルは、インタフェースを上げるとMACアドレスから作ったリンクローカルアドレスを付けるが、ルータ広告の処理はカーネルの外のプログラムに任せている。TessronOSでは`so_slaac.c`のタスクがこれを行う(RFC 4861、RFC 4862、RFC 8106、RFC 8981)。

タスクはリンクローカルアドレスの重複の確認が済むのを待ち、そのインタフェース識別子(アドレスの下位64ビット)を取る。次に、ICMPv6のルータ広告だけを受けるrawソケットを開き、全ルータのマルチキャストアドレス(ff02::2)にルータ要請を4秒おきに3回送る。以後は、設定がルータ広告を使わなくなるか(9.3.4)スタックが止まるまで広告を待ち、ケーブルが抜けて挿し直されたときにも要請をやり直す。

広告は、送信元がリンクローカルアドレスで、ホップ制限が255のもの(リンクの外からは送れない)だけを受け付ける。ホップ制限は受信の付随データ(`IPV6_RECVHOPLIMIT`)で知る。

- プレフィックス情報のうち、自動設定のフラグが立った64ビットのプレフィックスから、プレフィックスとインタフェース識別子を合わせたアドレスを作り、有効期間と推奨期間を付けて`neta0`に設定する(`rump_tsnet_setaddr6`)。オンリンクのフラグが立っていればプレフィックス長は64で、プレフィックスの経路も付く。新しいアドレスはカーネルが重複を確かめ、その間は送信元に使わない。推奨期間を過ぎたアドレスはカーネルが新しい接続の送信元に選ばなくなり、有効期間を過ぎたアドレスはカーネルが外す。
- 同じプレフィックスがまた広告されると有効期間を更新するが、残りが2時間を超えるアドレスを2時間より短くはしない(RFC 4862 5.5.3)。偽の広告でアドレスを消されないためである。
- ルータの寿命が0でなければ、送信元をデフォルトルータとして寿命の間覚え、覚えている最初のルータを経由するIPv6のデフォルトの経路を設定する(`rump_tsnet_defroute6`)。寿命が切れるか0の広告が来れば、次のルータに替えるか経路を外す。ルータは3つまで覚える。
- RDNSSのオプションが示すDNSサーバを、その寿命の間3つまで覚え、名前解決に使う(9.3.2)。

設定で一時アドレス(プライバシー拡張、RFC 8981)を使うときは、プレフィックスごとに、インタフェース識別子を乱数にしたアドレスも作る。一時アドレスの有効期間は2日、推奨期間は1日から乱数の値(最大でその10分の4)を引いたもので、どちらもプレフィックスの期間より長くはしない。推奨期間が切れる5秒前に次の一時アドレスを作り、古い一時アドレスは有効期間が切れるまで残すので、その上の接続は続けられる。乱数で作る識別子は、すべて0のものと、RFC 5453で予約された範囲を避ける。重複の確認で他のホストが使っていると分かったときは作り直し、3回まで試す。一時アドレスにはカーネルの`IN6_IFF_TEMPORARY`のフラグを立て、カーネルの送信元アドレスの選択(RFC 6724の規則7)が同じプレフィックスの安定したアドレスより一時アドレスを先に選ぶようにする(`ip6_prefer_tempaddr`)。安定したアドレスはそのまま残り、外からの接続を受けられる。コンソールには`net: IPv6 temporary address fec0::8c1d:2f0a:61e4:93b7 (86400 s)`のように表示する。DHCPv6は扱わない。

アドレスの表とルータ、DNSサーバはタスクだけが書き換える。タスクを止める`knl_so_slaac_stop`は、タスクがルータ広告の待ちから抜けるのを待ってから戻るので、止めた側がそのあとでアドレスを外せる。設定がルータ広告を使わなくなったときは、作ったアドレス(一時アドレスを含む)をインタフェースから外し、デフォルトの経路を消し、ルータが示したDNSサーバを忘れる。

作ったアドレスとデフォルトルータは`so_getifaddr6`で、DNSサーバは`so_getdns6`で読める(`T_SOIF6`にはアドレス、プレフィックス長、状態のフラグ`SO_IF6_`、有効期間と推奨期間の残りが入る)。起動時にはコンソールに`net: IPv6 address fec0::5054:ff:fe12:3456 (86400 s)`、`net: IPv6 default router fe80::2`のように表示する。

### 9.3.4 IPv6の設定と状態

ネットワーク設定の実身の`$$IPV6`の行(9.3)は、設定を読み込む`so_conf`が`so_setip6`と`so_setdns6`を呼んで`neta0`に反映する。設定が前と同じなら何もしないので、IPv4の設定や時刻サーバだけを変えたときに、IPv6のアドレスやその上の接続は影響を受けない。変わったときは、まず前の設定が付けたものを外し、それから新しい設定を付ける。

| 設定 | `so_setip6` | `neta0`のIPv6 |
| --- | --- | --- |
| `on auto` | `SO_IP6_AUTO` | リンクローカルアドレスと、ルータ広告から作るアドレス。デフォルトルータとDNSサーバもルータ広告から得る(9.3.3) |
| `on auto temp` | `SO_IP6_AUTO`と`SO_IP6_TEMP` | 上に加えて一時アドレス。新しい接続の送信元には一時アドレスを選ぶ |
| `on fixed` | `SO_IP6_FIXED` | リンクローカルアドレスと固定のアドレス(期間は無期限)。`$$IPV6GW`があればそれを経由するデフォルトの経路。ルータ広告は聞かない |
| `on none` | `SO_IP6_LINK` | リンクローカルアドレスだけ。デフォルトの経路はない |
| `off` | `SO_IP6_OFF` | IPv6を使わない。NetBSDのインタフェースの`ND6_IFF_IFDISABLED`を立て、カーネルは`neta0`でIPv6を送りも受けもしない。リンクローカルアドレスは確認中のフラグのまま残り、使われない。ループバックの::1は使える |

`off`から戻すと、カーネルはリンクローカルアドレスの重複をもう一度確かめる。`auto`に戻すと、ルータ要請からやり直し、以前と同じインタフェース識別子から同じ安定したアドレスを作る。固定のアドレスには、未指定、ループバック、リンクローカル、マルチキャストのアドレスは使えない(`E_PAR`)。`$$IPV6DNS`のサーバは`off`のとき以外、ルータが示したサーバより先に尋ねる(9.3.2)。

今のIPv6の状態は、システムの実身のレコード7(8.4)にIPv4の状態と並べて次の行で出す。ネットワーク設定の小物の〈ＩＰｖ６〉〈状態〉はこれを読んで表示する。

```text
IPV6 <off|none|fixed|auto|auto temp>
ADDRESS6 <アドレス>/<プレフィックス長> <link|auto|temp|fixed> <有効期間の残り> <推奨期間の残り> [tentative] [duplicated] [deprecated]
GATEWAY6 <デフォルトルータ>
DNS6 <DNSサーバ>
```

`ADDRESS6`はインタフェースのアドレスごとの行で、種類はリンクローカルアドレス、ルータ広告から作ったアドレス、一時アドレス、固定のアドレスである。期間の残りは秒で、期限がなければ`infinite`である。そのあとに、重複の確認中、他のホストが使っている、推奨期間を過ぎた、のフラグが付く。`DNS6`は尋ねる順に並ぶ。

lwIPのスタック(`NETSTACK=lwip`)はIPv6を持たないので、`so_setip6`は`SO_IP6_OFF`以外に`E_NOSPT`を返し、`so_getip6`は常に`SO_IP6_OFF`である。

## 9.4 時刻合わせ

SNTPクライアントは、インタフェースにIPアドレスが設定されるとNTPサーバに問い合わせ、システム時刻を合わせる。NTPサーバは設定の`$$NTP`の行で指定する。電池のないRaspberry Pi 5は起動のたびに1985年から計時を始めるので、ネットワークに接続していれば、ここで正しい時刻になる。

## 9.5 カレンダ

T2EXのカレンダ関数`dt_`を提供する。`dt_strftime`以外はプロセスからもSVCクラス3で呼べる。

| 関数 | 機能 |
| --- | --- |
| `dt_gettime`、`dt_settime` | システム時刻を秒単位で取得する、設定する |
| `dt_gmtime`、`dt_localtime` | 秒を年月日時分秒に変換する |
| `dt_mktime` | 年月日時分秒を秒に変換する |
| `dt_strftime` | 日時を文字列に整形する |
| `dt_getsystz`、`dt_setsystz` | システムのタイムゾーンの標準時の差を取得する、差だけで設定する |
| `dt_getsyszone`、`dt_setsyszone` | タイムゾーンのIANAの名前を取得する、名前と標準時の差で設定する |

時刻を設定できるのは時計の実身への書込み権限を持つユーザで、デフォルトでは管理者だけである。タイムゾーンは実身「暦」のメタデータに、UTCからの東向きの標準時の差を分単位で`tessronos.calendar.tz`に、IANAのタイムゾーンの名前(`Asia/Tokyo`など、48バイト未満の英数字と`/_+-`)を`tessronos.calendar.zone`に格納する。デフォルトは540分と`Asia/Tokyo`で、再起動しても保持される。名前のない古い暦は、差が540分なら`Asia/Tokyo`とみなす。`dt_setsystz`で差だけを変えると名前は空になる(同じ差を設定したときは名前を残す)。

`dt_localtime`と`dt_mktime_local`は、名前が次の地域のものなら夏時間に従い、夏時間の間は差に60分を足し、`tm_isdst`を1にする。カーネルはタイムゾーンのデータベースを持たず、規則を表で持つ。

| 規則 | 名前 | 夏時間の期間 |
| --- | --- | --- |
| 米国とカナダ | `America/Anchorage`、`Los_Angeles`、`Denver`、`Chicago`、`New_York`、`Halifax` | 3月の第2日曜2時から11月の第1日曜2時(現地) |
| 欧州連合 | `Atlantic/Azores`、`Europe/London`、`Paris`、`Berlin`、`Athens` | 3月の最終日曜から10月の最終日曜、1時(UTC) |
| 豪州の南東部 | `Australia/Adelaide`、`Sydney`、`Melbourne` | 10月の第1日曜2時から4月の第1日曜3時(現地) |
| ニュージーランド | `Pacific/Auckland` | 9月の最終日曜2時から4月の第1日曜3時(現地) |

夏時間の終わりに2度来る1時間の現地時刻を`dt_mktime_local`でUTCにすると、夏時間の方になる。タイムゾーンのデータベースを持つプログラム(ブラウザのICU、14.4)は名前を使い、その地域の過去の規則も含めて扱う。名前は、ユーザ環境設定の〈個人属性〉で地域を選ぶと設定される(11.3)。カーネルの試験`time`の群の`test_zone_name`が、名前の保存と読み戻し、差だけの設定で名前が消えること、米国と欧州連合の夏時間の始まりと終わりの前後、豪州とニュージーランドの夏と冬、日本の通年の時刻と、その逆の変換、誤った名前の拒否を確かめる。

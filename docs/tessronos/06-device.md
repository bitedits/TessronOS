# 第6章　デバイス

## 6.1 デバイス管理

デバイスは、μT-Kernel 3.0のデバイス管理機能で扱う。ドライバは`tk_def_dev`でデバイスを名前で登録し、利用側は`tk_opn_dev`で開いて`tk_rea_dev`、`tk_wri_dev`で読み書きする。パーティションを持つディスクは、パーティションをサブユニットとして見せる(`sda`がデバイス全体、`sda0`が第1パーティション)。パーティションはGPTの項目か、MBRの基本区画と拡張区画の中の論理区画(EBRの連なり)である。GPTは区画表の項目の数(4096まで)を見て、使われている項目を1台に255まで、MBRは基本区画と論理区画を合わせて255まで持つ(`BLK_MAX_PART`)。サブユニットの番号は0から254で、名前は`uda254`のようになる。区画表の無いディスク(スーパーフロッピー)は全体が1つのボリュームである。区画表を書き換えた後で、ディスク全体のデバイスに属性`TDN_PARTSCAN`を書き込むと、SD、virtio-blk、USBのディスクのドライバが区画表を読み直す。ドライバは、広がった区画の大きさと足された区画を、すでにある区画の番号を変えずに反映し、デバイスを登録し直す(7.7)。登録できるデバイスは192、同時に開けるデバイスは4096、同時の要求は256、同時に扱うディスクは160である(7.6)。

登録するデバイスは次のとおりである。

| 名前 | 種類 | ハードウェア |
| --- | --- | --- |
| `sda` | ディスク | SDカードかeMMC(SDHCI) |
| `vblka`、`vblkb` … | ディスク | virtio-blk(QEMU) |
| `uda`、`udb` … `udz`、`udaa` … | ディスク | USBマスストレージ。接続した順に、空いている一番小さい番号で名前が付く。`udz`の次は`udaa`、`udab` … `udaz`、`udba`のように、表計算の列の名前と同じ付け方で続く。128台まで(`MSC_MAX`) |
| `neta` | ネットワーク | Ethernetかvirtio-net。1回の読み書きが1フレーム |
| `snda` | サウンド | USBオーディオ、RP1のI2S、HDMI(Raspberry Pi 5) |
| `cama` | カメラ | USBビデオクラスのカメラ。`cama0`から`cama3`が来た順のカメラ |

次のものはデバイス管理には登録しない。このうち実身があるものは、デバイスマネージャが実身として見せ、プログラムは実身を通して使う(8.4)。

| もの | 扱い | 実身 |
| --- | --- | --- |
| コンソールのUART | カーネル内の関数(`tm_`) | なし(起動の最初から使う) |
| RTC | カーネル内の関数。時刻は時計の実身で見せる | 時計 |
| 乱数 | 実身。カーネル内の利用者は`ts_get_random` | 乱数(`OB_S_CHAR`) |
| 画面 | 実身。描画の層は`ts_disp_`を直接使う | 画面(`OB_S_DISPLAY`) |
| USBのキーボードとマウス | 実身。ウインドウマネージャは`ts_hid_read`で受け取る | インタフェースごとのキーボード、ポインタと、入力(`OB_S_INPUT`) |
| GPIOのバンク(Raspberry Pi 5、4) | 実身。ドライバがピンを機能に割り当てる処理は`gpio_`、`rp1_gpio_`を直接使う | バンクごと(`OB_S_GPIO`) |
| USBデバイス(ハブを含む) | 実身 | デバイスごと(`OB_S_USB`) |

デバイスは実身としても扱える。デバイスの実身に対するレコードの読み書きが、そのままデバイスの読み書きになる(第8章)。デバイスのUUIDは最初に検出したときに生成してデバイス箱に記録するので、次回の起動でも同じ実身として見つかる。USBメモリのように抜き差しのあるデバイスの接続・切断、メディアの挿入・取出しは、そのデバイスの実身とデバイス一覧の実身へのイベントとして通知される。ディスクのボリュームは、デバイスの実身を通して`fs_attach_dev`で要求すると`/media`の下にデバイス名でマウントされ、デバイスが切断されるとアンマウントされる。fimpの名前を渡さなければ、区画の先頭の中身から形式を見分けてマウントする。ディスクの実身の属性`tessronos.format`に、見分けた形式(`kind`)、ラベル、マウントするfimpが現れる(7.6)。媒体が抜かれると、その区画に取り付けてあった実身のボリュームも去ったものになる。

## 6.2 ドライバ

| ハードウェア | ファイル | マシン | 状態 |

| GPIO | `device/gpio/gpio_bcm2711.c` | Pi 4系 | 58本のピンとACT LED(GPIO 42)。3つのバンクの実身。コンソールのピンとボードの配線のピンは実身から変更できない(3.6.4) |

PCIeのコンフィギュレーション空間はECAMで読み、列挙時にBARを割り当てる。Raspberry Pi 5では、RP1が接続されたPCIeのルートコンプレックスをカーネルが自前で初期化し、RP1のアドレスウインドウを通してUSB、Ethernet、GPIO、UARTにアクセスする。PCIeデバイスのMSIはエッジトリガで受け付ける。Raspberry Pi 4系のルートコンプレックスは、コンフィギュレーション空間を索引のレジスタと4KBのウインドウで見せるので、`pcie_rc.c`が読み書きの関数を共通の列挙(`kernel/sysman/pcie.c`、`PCIE_CFG_BOARD`)に渡す。BARのPCIeのアドレスとCPUから見たアドレスは外向きのアドレスウインドウの分だけずれる(`PCIE_BAR_CPU_OFFSET`)。MSIは使わず、INTAをレベルトリガで受け付ける。

Raspberry Pi 5とCM5で配線が違うところ(SDHCIの先がSDカードかeMMCか、カード検出線の有無、ボードが使う常時オンのGPIO、EthernetのPHYのアドレス、コンソールのポート)は、ドライバがボードの表(`include/ts/board.h`の`knl_board`)を見て切り替える。表は起動時にデバイスツリーとファームウェアのボードのリビジョンから選ぶ(3.5.1)。Raspberry Pi 4、400、CM4も同じ表で見分ける(3.6.1)。

シリアルポートは、ポートごとのデバイス`sera`、`serb`…(種類`TDK_SERIAL`、サブユニットなし)である。プロセスは、デバイスを直接開かず、SVCのクラス11(`sr_`、付録A、`device/ser/ser_svc.c`)で使う。`sr_lst_prt`がポートの一覧を返し、`sr_opn_prt`で開いたポートはプロセスの中の番号で指定する。デバイスはカーネルがプロセスに代わって開いて持ち(全体で8つまで)、プロセスが終わると閉じる。読み書きのバイト列はカーネルのメモリを通して受け渡す。読出しの待ち時間は呼出しごとに指定し、ポートの受信の待ち時間をそれに設定してから読む。ブラウザのWeb Serial(14.4.9)がこれを使う。

## 6.3 USB

USBスタックは、xHCIホストコントローラの上に、ハブ、HID、マスストレージ、オーディオ、ビデオのクラスドライバを載せたものである。Low、Full、High、Superのすべての速度と、コントロール、バルク、インタラプト、アイソクロナスの各転送を扱う。デバイスの抜き差しは、専用の管理タスクがハブの状態変化を受けて処理する。管理タスクは、デバイスが来たり去ったりすると、ロックを放した後でUSBデバイスとキーボード、ポインタの実身を一覧に合わせる(`knl_obusb_changed`)。ハブを含めて192台のデバイスを扱い(`USB_MAX_DEV`)、xHCIのスロットはコントローラが持つ数(255まで)を使う。

| クラス | 機能 |
| --- | --- |
| HID | キーボードとマウス。レポートディスクリプタを解析し、相対座標と絶対座標のどちらも扱う |
| マスストレージ | Bulk-Only TransportとSCSI。パーティションテーブルを読み、パーティションをサブユニットにする。CD-ROMドライブ(INQUIRYの周辺機器の種類5)も同じ名前の付け方のディスクにし、ブロックは2048バイト、読み取り専用、取り外せるものとして扱い、パーティションは読まない(ディスクの属性は`TDK_DISK_CDROM`)。BTRONのCD-ROMはファイル変換が読む(11.9) |
| オーディオ | UAC 1.0。アイソクロナス転送で再生と録音をする |
| ビデオ | UVC 1.0から1.5。カメラデバイス`cama`のカメラにする(6.6) |
| ハブ | USB 2.0とSuperSpeed |

### 6.3.1 プログラムのUSBデバイス

クラスドライバが取らなかったデバイス(役割が`USB_ROLE_NONE`で、ハブでないもの)は、プログラムが使える(SVCのクラス12、`us_`、`device/usb/uusb.c`、付録A)。プログラムはデバイスの一覧と記述子を読み、そのようなデバイスを開く。開けるのは一度に1つのプロセスだけで、クラスドライバのデバイスや別のプロセスが開いているデバイスは`E_BUSY`になる。開いたデバイスには、プロセスの中の番号が与えられる。プログラムはその番号で、コントロールエンドポイントに要求を出し、インタフェースの代替設定を選び、エンドポイントの停止を解き、デバイスをリセットし、選んだ設定のバルク、インタラプト、アイソクロナスのエンドポイントでデータを送受する。デバイスが抜かれると、以後の呼出しは`E_NOEXS`になる。プロセスが終わると、開いていたデバイスは閉じる。

コントロールの要求とOUTの転送は、管理タスクのロックを持ったまま、その時間切れ(最長10秒)まで行う。INのエンドポイントは、ロックを持ったまま待たない。最初のINの転送でそのエンドポイントにストリームを開き、管理タスクが転送の完了を受けるたびに、そのバイト列を1つのチャンクとしてエンドポイントのリング(64KB)に入れる。INの転送は一番古いチャンクを取り出す。チャンクがなければ、ロックの外で時間切れまで待つ。求めた長さより長いチャンクは切り詰め、残りは捨てる。リングがあふれると古いチャンクから捨てる。アイソクロナスのINも同じ作りで、1サービス間隔のパケットが1つのチャンクになる。アイソクロナスのOUTにもストリームを開き、コントローラがサービス間隔ごとにパケットを求める。OUTの転送はバイト列を1つのパケットとしてリングに入れて戻り、リングが満ちているときだけ空くまで待つ。送るパケットのないサービス間隔は何も送らない。代替設定を選ぶとき、停止を解くとき、リセットのときはストリームを閉じ、次の転送で開き直す。リセット(`us_rst_dev`)は、デバイスのスロットを手放し、ポートをリセットし、デバイスにアドレスを付け直して元の構成にする(`knl_usb_reset_device`)。デバイスはツリーの中の場所と番号と記述子を保ち、プロセスは開いたまま使い続けられる。プログラムのストリームが開いている間は、管理タスクは4ミリ秒ごとにコントローラを見る。

HIDのクラスドライバはキーボードかポインタのインタフェースだけを取る。それ以外のHIDの機器(ゲームパッド、FIDOのキーなど)は役割が`USB_ROLE_NONE`のまま残り、プログラムが使える。ブラウザのWebHIDはそれを使う。バイト列はカーネルのバッファを通し、`knl_ua_get`と`knl_ua_put`で受け渡す(PAN)。ブラウザのWebUSB(14.4.8)がこれを使う。

### 6.3.2 試験のソフトウェアのUSBコントローラ

試験のマシン(QEMU)にない種類のUSBの機器(ゲームパッド、MIDIの機器)を、管理タスク、クラスドライバ、プログラムのUSBデバイス(6.3.1)を通して端から端まで試すために、`KTEST=1`のQEMUのビルドだけにソフトウェアのUSBコントローラがある(`device/usb/vhc.c`、`vhc.h`)。ポートは2つで、試験が`knl_vhc_plug`で機器を挿すと、初めのときにコントローラを管理タスクに足し(`knl_usb_add_hc`)、ポートを見直させる。機器は、デバイス、コンフィギュレーション、文字列、HIDのインタフェースのレポートの記述子と、OUTのエンドポイントに送られたものを受ける関数、クラス要求に答える関数で表す。標準の要求(アドレス、コンフィギュレーション、代替設定、停止)とHIDの答えの要らないクラス要求はコントローラが受ける。試験が`knl_vhc_in`で置いたINのエンドポイントのデータは、管理タスクがコントローラを回すときに、そのエンドポイントのストリームに1回の転送ずつ渡る。ブラウザの試験`test_blink_pad`と`test_blink_midi`が使う(14.10)。

## 6.4 キーボードとポインタ

キーボードとマウスの入力は、USBのHIDから入力キューに入り、ウインドウマネージャが読み出す。同じイベントのコピーを、インタフェースごとの実身と入力の実身がレコード1で見せる。コピーを読んでもキューからは取り出さない。試験などが与える入力は、入力の実身のレコード1に書き込み、キューに入る(8.4)。ユーザ環境設定で変更できる入力の属性、たとえばキー入力の受付時間、キーリピート、ポインタの速度と加速度、主ボタンの左右の入れ替え、中ボタンのダブルクリック割当て、一時シフトは、このレイヤで適用する。ホイールは縦と横の回転量として通知される。

HIDのインタフェースは次のように準備する。ブートサブクラスのキーボードは、SET_PROTOCOLでブートプロトコルに切り替え、SET_IDLE(0)を送り、SET_REPORTでLEDをすべて消す。LEDが一度設定されるまでレポートを送らないキーボードがあるためである。8バイトのブート形式のレポートを読み、キーの配列にErrorRollOverなどの誤り(値1から3)があるときは、キーの状態を前のレポートのままとし、修飾キーだけを更新する。同時押しが多すぎたときに、押されているキーを離して押し直したことにしないためである。

ポインタは、レポートディスクリプタ(4096バイトまで。失敗したら20ms置いて3回まで要求する)を解析する。解析は、Push/Popを含むグローバル項目、4バイト形式のUsage、レポートIDごとのビット位置を扱い、X、Y、ホイール、AC Pan、ボタンの変数フィールドだけを保持する。保持しないフィールドも、後に続くフィールドの位置には長さをすべて加える。相対のX、Yは、Logical Minimumが0以上と書かれていても符号付きとして読む。移動量は両方向にあり、符号なしとして読むと左や上への小さな移動が画面の端まで飛ぶためである。X、Yは同じレポートのものを組にし、相対のものを絶対のものより優先する。ディスクリプタが使えないブートサブクラスのマウスは、ブートプロトコルに切り替えて3から4バイトのレポートを読む。

ディスクリプタどおりに読むブートサブクラスのマウスには、SET_PROTOCOLでレポートプロトコルを要求する。ブートローダがブートプロトコルのまま残した機器が要求に従わないことがあるため、3から4バイトのレポートで、ディスクリプタにないレポートIDで始まるもの、またはディスクリプタのX、Yがその長さに収まらないものが来たら、以後はブート形式として読む。

インタラプト転送の長さは、ふつうはwMaxPacketSizeとする。ポインタのレポートがそれより長いときは、ディスクリプタにある最長の入力レポートの長さ(64バイトまで)とし、複数のパケットに分かれたレポートを1回の転送で受け取る。ポーリング間隔は、LowとFull SpeedではbIntervalをミリ秒として2のべき乗に切り捨て、High Speed以上では2^(bInterval-1)マイクロフレームとする。転送の誤りでエンドポイントが停止したら、Reset EndpointとCLEAR_FEATURE(ENDPOINT_HALT)で再開する。正常な転送を挟まずに8回を超えて停止したら、再開をやめる。ポインタは、ディスクリプタから読み取った配置と最初の12個のレポートをシリアルに出力する(`usb: hid:`)。

## 6.5 サウンド

サウンドデバイス`snda`は、B-right/Vのサウンドデバイスの仕様(データ番号と構造体、`include/ts/snd.h`)に従う。その仕様向けに書かれたプログラムはそのまま使える。

| データ番号 | 内容 |
| --- | --- |
| 0、1 | 再生するPCMを書き込む。録音したPCMを読み出す |
| `DN_SDPCMMODE` | サンプリングレート(8kHzから48kHz)、形式(μ-law、8bit、16bit)、モノラルとステレオ |
| `DN_SDPCMCTL` | 停止、再生、録音、繰り返し再生 |
| `DN_SDPCMCNT`、`DN_SDPCMENDCNT` | 処理したバイト数と、停止するバイト数 |
| `DN_SDPCMBUFSZ` | PCMバッファのサイズ(デフォルト32KB、最大1MB) |
| `DN_SDGAININ`から`DN_SDVOLAUX2` | 入力と出力の音量 |
| `DN_SDSTAT` | TessronOSの追加。再生している出力先の種類、標本化周波数、チャネル数、渡したフレームの数など(`SDStat`) |
| `DN_SDOUTS` | TessronOSの追加。出力先の一覧(`SDOut`の並び。先頭は自動) |
| `DN_SDOUTSEL` | TessronOSの追加。選んだ出力先と、いま鳴らしている出力先(`SDOutSel`) |
| `DN_SDMIXER`、`DN_SDMIXSET` | TessronOSの追加。ミキサーの全体とプログラムごとの音量と消音を読む、設定する(6.5.6) |

チャネルはプロセスとユニットの組ごとに1つ持ち、複数のプログラムが同時に鳴らした音はミキシングして出力する。

### 6.5.1 出力先

サウンドデバイスは、そのとき使える出力先の1つで鳴らす。出力先はIDで呼び、IDは起動をまたいで変わらない。

| ID | 出力先 |
| --- | --- |
| `auto` | 自動。次の順で、そのとき音を出せる最初の出力先 |
| `usb:VVVV:PPPP@C-R.h` | USBオーディオの機能。VIDとPID(16進)と挿した場所(コントローラの番号、ルートポート、ハブのポート) |
| `i2s` | Raspberry Pi 5のI2S0(GPIO 18〜21)のDAC |
| `hdmi0`、`hdmi1` | Raspberry Pi 5のHDMIのポート |

自動の順は、USBオーディオの機能(来た順)、I2S、HDMI0、HDMI1である。I2SのDACはつながっているかどうかを確かめる手段がなく、I2Sはいつも出力先として出るので、Raspberry Pi 5で自動の出力先がHDMIになることはない。HDMIで鳴らすには選ぶ。

出力先は、システムの実身のレコード8に`SELECT ID`を書くと選べ、すぐに切り替わる。機器の設定の実身に`SOUND_OUT ID`の行を書くと、カーネルが起動時とその実身が書き換えられたときに読み(`outer_kernel/wm/uconf.c`)、次の起動からも使う。システム環境設定は両方を書く(11.6)。選んだ出力先がないとき(USBの機器を抜いた、HDMIの画面が音を受けない)は、自動の順で選んだ先で鳴らす。再生中は0.5秒ごとに出力先を選び直し、選んだ出力先が戻れば(挿し直せば)そこへ移る。USBの機能は、同じIDのものがなければ、同じVIDとPIDのものを別の場所に挿したものとみなす。

切り替えは再生中でもできる。今のバックエンドを止め、新しい出力先で始め直す。チャネルは止めず、次のフレームから新しい出力先の標本化周波数に変換して続ける。鳴らしている出力先の機器が去ったときも、すぐに次の出力先へ移る。行き先がないときだけチャネルを止める。移ったことはコンソールに出す(`snd: the stream moves from A to B`)。

プログラムは、出力先の一覧を`DN_SDOUTS`で、選んだものと鳴らしているものを`DN_SDOUTSEL`で読む。一覧の各項目(`SDOut`)は、ID、つながっている機器の名前(USBの機能の製品名、HDMIの画面のEDIDの名前)、種類、フラグ(選ばれている、鳴らしている、いまは音を出せない、音量がある)、鳴らしている間の標本化周波数とチャネル数である。サウンドデバイスの実身ではレコード24と25にあたる(8.4)が、実身からは選べない(`E_RONLY`)。出力先はシステム全体の設定なので、保護されたシステムの実身のレコード8で選ぶ(付録Aの権限の表)。レコード8は、`OUTPUT`(鳴らしている出力先のID、ないときは`none`)、`SELECT`(選んだ出力先)、`RATE`、`CHANNELS`の行と、出力先ごとの`OUT`、`OUT_KIND`(`usb`、`i2s`、`hdmi`。自動は`none`)、`OUT_FLAGS`(`SND_OF_*`)、`OUT_NAME`の組を持つ。

### 6.5.2 RP1のI2S

Raspberry Pi 5は、ヘッダのGPIO 18〜21につないだDACボード(PCM5102Aの類)に、RP1のI2S0から出す(`device/snd/snd_rp1.c`)。音声のPLLを1536MHz(50MHzの水晶の30.72倍)にして25で割った61.44MHzを作り、clk_i2sでさらに20で割って3.072MHzのビットクロックにする。48kHzで1フレーム64クロック(32ビットのスロットが2つ)である。DMAは、256フレームのブロック16個(85ミリ秒)のリングを、I2S0の要求に合わせて送信のFIFOに運ぶ。割込みは使わず、USBの管理タスクが数ミリ秒ごとにDMAの位置を見て、終わったブロックに次の音を詰める。

I2S0のステレオの組ごとの送信と受信の許可(TERとRER)は、リセットの後に有効になっている。DMAのレジスタに書いたワードは有効な送信の組に順に配られるので、4組とも有効のままだと1フレームに8ワードを取り、音が4倍の速さで進む。設定の前に4組すべてを無効にし、第1組だけを有効にする。2026年10月8日の実機の記録では、ブロックが毎秒700ほど(48kHzの約3.7倍)進み、動画が早回しになった。この直しはその原因と見ているが、実機で未確認である。

確かめるために、流れを始めた直後に次の行をコンソールに出す。

| 行 | 内容 |
| --- | --- |
| `i2s0 clocks:` | RP1の周波数計で数えたpll_audio、pll_audio_sec、clk_i2sの周波数(clk_i2sは3072kHzになるはず)と、PLLのレジスタから計算したpll_audio_core、clk_i2sのレジスタ |
| `i2s0 interface:` | I2S0の送信の組の数、CCR、TERの今の値と最初に見つけたときの値、TCR、TFCR、DMACR |
| `i2s0: N blocks in M ms, X a second` | リングの進み。始めてから30秒は5秒ごと、その後は60秒ごと。48kHzなら毎秒187.5ブロック |

PLLがすでに同じ設定でロックしていれば作り直さない。比べるのは、ロック、参照の分周(REFDIV)が1であること、電源のレジスタ(PWR)がすべて動作中(端数を使うのでDSMPDも0)であること、FBDIVの整数と端数、PRIMの2つの分周である。

### 6.5.3 HDMIの音(Raspberry Pi 5)

画面はファームウェアが出し続け(10.2)、カーネルはHDMIの映像の設定に触れない。音に要るものはHDMIのコントローラの中にあり、`device/snd/snd_hdmi.c`だけが扱う。

| もの | 内容 |
| --- | --- |
| MAI | コントローラごとの音声の入力。2つのコントローラが共有する`hd`のブロックにある。IEC 60958のサブフレームのFIFOと、DVPの108MHzから作る標本化のクロック(2250で割って48kHz)、形式(48kHz、PCM、2チャネル) |
| HDMIの本体 | 音声パケットの設定(使うチャネル、平坦なサンプルを0にする)、音声クロックの再生のNとCTS(Nは6144、CTSは画素クロックのkHzの値)、パケットRAMのAUDIO InfoFrame(2チャネル、ほかは流れのとおり) |
| DMA | 40ビットのDMA(`dma40`)のチャネル6。256フレームのブロック16個のリングの制御ブロックを回し、MAIの要求(HDMI0はDREQ 10、HDMI1は17)に合わせてFIFOに運ぶ |

サンプルは1フレーム2ワードのIEC 60958のサブフレームにする。下位4ビットがプリアンブル(192フレームごとの先頭の左が8、ほかの左が2、右が4)、24ビットの音声の欄の上位16ビット(ビット12〜27)がサンプル、ビット30がチャネルの状態、ビット31がビット4〜30の偶数パリティである。チャネルの状態は、民生用、PCM、著作権の主張なし、48kHz、16ビットを表す。DMAは止まらずにリングを回るので、管理タスクが見に来るのがリングの4分の3より遅れたときは、リングを一周したものとして、DMAがいるブロックのほかをすべて詰め直す(古い音が繰り返して聞こえる)。

どのポートを使えるかは、起動時にファームウェアに尋ねる。ファームウェアが駆動している画面とその番号(2がHDMI0、7がHDMI1)、画面のEDID(名前の記述子と、CEAの拡張の基本の音声のフラグか音声データブロック)、画素クロック(画面の表示のタイミング)である。ファームウェアが駆動していないポートのレジスタには触れない(クロックが入っていないことがある)。流している間は1秒ごとにポートを見て、ホットプラグの線が抜けた、DVIになった、表示のタイミングのレジスタ(HORZA、VERTA0、VERTB0)が変わった(モードが変わった)ときは流れを終える。サウンドデバイスはそれを出力先が去ったものとして選び直し、HDMIがまだ音を出せれば、その時の画素クロックでCTSを作り直して始め直す。ファームウェアが画面の一覧に答えないときは、どのポートが画面を出しているか分からないので、HDMIの音を扱わない。DVIで出している画面、EDIDにCEAの拡張がないか音の記述がない画面、ホットプラグの線が抜けているポートは、「いまは音を出せない」出力先として一覧に出し、選んでも鳴らさない。MAIの閾値のレジスタは、BCM2712のD0のステッピング(表示のハードウェアHVSのバージョンが0x54)で配置が違うので、バージョンを見て書き分ける。

流れを始めると`hdmiN plays at 48000 Hz`の行に画素クロック、MAIの制御、HDMIの方式、パケットの設定を出し、リングの進みをI2Sと同じ形で出す(`hdmiN: N blocks in M ms`)。`config/config.h`の`CNF_SND_HDMI`を0にすると、HDMIの音を扱わない(レジスタに触れない)。実機で未確認である。

### 6.5.4 実機での確認

QEMUにはI2SもHDMIの音もないので、出力先の選択と切替えはUSBオーディオの機能でカーネル内の試験(`ktest_snd`の`test_outputs`。2つ目の機能をQEMUのモニタで挿し、選び、再生中に切り替え、選んだ機能を抜いて自動の先に移ることと、挿し直して戻ることを見る)で確かめ、I2SとHDMIは実機で確かめる。`make SNDTEST=1`を付けたRaspberry Pi 5のイメージは、起動の25秒後に次の確認を順に行い、コンソールに`sndtest:`の行を出す(`kernel/sysdepend/rpi5/sndtest.c`、build-and-run.mdの4.6.1)。どれも小さな440Hzの音を鳴らし、時間の上限を持ち、失敗しても次に進む。

| 確認 | 合格の条件 |
| --- | --- |
| `outputs` | 出力先が自動を含めて2つ以上あり、`i2s`がある |
| `i2s` | clk_i2sの実測が3072kHzの1%以内、リングの進みが2秒間で毎秒187.5ブロックの3%以内 |
| `hdmi0`、`hdmi1` | リングの進みが毎秒187.5ブロックの3%以内。音を出せないポートは飛ばす |
| `usb` | USBオーディオの機能が毎秒48000フレームの5%以内を取る。機能がなければ飛ばす |
| `move` | 1つのチャネルを鳴らしたまま、音を出せる出力先を順に選び、どれでもチャネルが鳴り続け、処理したバイト数が進む |

### 6.5.5 システムの音を鳴らすインタフェース

システムの音(ブザー、押下音、離し音、画面印刷の秒読み、設定の小物の〈試聴〉)は、すべてウインドウマネージャの音のモジュール(`outer_kernel/wm/beep.c`)が鳴らす。このモジュールは自分のタスクでサウンドデバイスの実身を開き、1つのチャネルとして書くので、どれも選んだ出力先(6.5.1)で鳴る。音ごとにチャネルを一度止めてから書き直すので、前の音が途中で切られても次の音は断られない。

| 呼び方 | 待つか | 内容 |
| --- | --- | --- |
| `wm_beep(what)` | 待たない | ウインドウ層とデスクトップのクリック音、ブザー、秒読み。スピーカーを切っている(`LK_SPEAKER`が0)ときは鳴らさない。最後に頼まれたものを鳴らす |
| `wm_beep_try(what)` | 鳴り始めるまで待つ(3秒まで) | 〈試聴〉。スピーカーを切っていても鳴らし、鳴り始めたら`E_OK`、音を出せる出力先がなければ`E_NOSPT`を返す |
| システムの実身のレコード8に`PLAY 音 [tone]` | 同上 | プロセスから`wm_beep_try`を呼ぶインタフェース。音は`buzzer`、`press`、`release`、`tick`、`long`、`test`(880Hzを0.5秒)。`tone`を付けると、レコード1にWAVがあっても、メタデータの高さと長さの音を鳴らす(ユーザ環境設定が設定中の音を聞かせるため)。書込みの戻り値が鳴ったかどうかである |

音の流れの止め方は、既定ではLinuxのPipeWireやPulseAudioと同じにする。鳴り始めに無音を足さず(`SNDHW`の`lead_ms`はどの出力先も0)、音は遅れない。最後のチャネルが止まっても、しばらくは無音を送り続けてから流れを止める(`tail_ms`)。HDMIは5秒、I2Sは2秒、USBオーディオは0である。その間に次の音が来れば、流れは続いているので欠けない。止まった後の次の音は、無音を足さずにすぐ流れを開き直して鳴らす。

HDMIの画面やテレビは、音のパケットが始まってから数百ミリ秒たってから音を出し始めることが多く、流れを開き直した直後の短い音(100ミリ秒のブザー)は欠けることがある。そのため、システム環境設定のサウンドのページに「出力を止めずに流し続ける」のスイッチを置く(11.6、既定は切)。入れると(`knl_snd_keep`、システムの実身のレコード8に`KEEP 1`、機器の設定の`SOUND_KEEP 1`で次の起動にも残る)、選んだ出力先の流れを、鳴らすものがなくても止めずに無音を送り続ける。鳴らすものが何もないときにも流れを始め、止めるのは、出力先を替えたとき、出力先が去ったとき(USBの機器を抜いた、HDMIの画面が抜かれたかDVIになったか表示のモードが変わった)だけで、その後すぐ選び直した先でまた始める。流れが止まっている間も0.5秒ごとに出力先を探し、来たら始める。

このスイッチはどの出力先にも効かせる。I2SのDAC(PCM5102Aの類)は、ビットクロックとフレームクロックが入り続け、0のサンプルが続いても困らない(続く0は自分で消音にする)。止めて開き直すたびに出ることのあるクロックの切れ目の雑音が無くなる分、むしろ良い。USBオーディオの機器も、無音のアイソクロナス転送が続くだけである。代わりに、流れている間はUSBの管理タスクが数ミリ秒ごとに起きてリングを満たすので、そのわずかな処理がずっと続く。既定を切にしているのはそのためである。

試験は`ktest_snd`の`test_keep`で、既定では音が終わると流れが止まること、`KEEP 1`で鳴らすものがないまま流れが始まり、音が終わった後も流れ続けること、`KEEP 0`で止まること、機器の設定の`SOUND_KEEP`から入ることを確かめる。画面は`tools/tests/ui_sound.steps`で、スイッチを入れると流れが始まり、切ると止まることを見る。QEMUにはHDMIとI2Sがないので、HDMIの5秒の続きと画面の変化による止まり方は実機で確かめる。

### 6.5.6 ミキサー

いくつものプログラムが同時にサウンドデバイスを開いて鳴らすと、それぞれのチャネルの音を混ぜて1つの流れにする。チャネルはプロセスとユニットの組(`snda`、`snda0`から`snda3`)ごとに1つで、同時に16まで持つ。1つのプロセスがいくつもの流れを持つとき(ブラウザ)は、ユニットを分けて開く。カーネルのタスク(ブザーとクリック音のタスク)はタスクごとのチャネルを持つ。

| 段 | すること |
| --- | --- |
| プログラムの音量 | チャネルのサンプルに、そのプログラムの音量の2乗を掛ける(50なら4分の1、12dB下がる)。消音なら0を掛ける |
| 混ぜる | 鳴っているチャネルを足す |
| 全体の音量 | 足したものに、左と右それぞれの全体の音量の2乗を掛ける。消音なら0 |
| ソフトリミッタ | 16ビットに収める。絶対値が24576(0.75)までは、そのまま、それを超えた分`e`は`24576 + 8191 × e / (e + 8191)`に曲げる。32767に近づくが届かず、境目で傾きが1のまま続くので、切ったときのような濁った音にならない |

プログラムは、プログラムの実身で区別する。同じ実身から起こしたプロセスは同じ音量に従い、その音量は次にそのプログラムが鳴らすときと、次の起動でも効く。プログラムの実身を持たないプロセス(ファイルから起こしたもの)は、プロセスごとに音量を持ち、プロセスが終わると忘れる。カーネルのタスクの音はまとめて「システムの音」(番号0)である。

全体の音量はソフトウェアで掛け、I2S、HDMI、USBオーディオのどの出力先でも同じに効く。USBオーディオの機器が自分の音量(フィーチャーユニット)を持っていても、全体の音量はそれを動かさない。機器の音量は機器を挿したときのままで、プログラムは`DN_SDVOLMAIN`で別に変えられる。こうしておくと、出力先を切り替えても聞こえる大きさが変わらない。

| データ番号 | 実身のレコード | 内容 |
| --- | --- | --- |
| `DN_SDMIXER` | 26 `OB_SND_MIX` | 読む。全体の音量(左と右)と消音、最近の大きさ、音のデバイスで鳴らしたことがあるプログラムの一覧(`SDMixApp`。プログラムの実身のUUID、プロセスの番号、名前、音量、消音、チャネルの数、鳴っているチャネルの数、最近の大きさ)。読むか設定するだけのチャネル(ミキサー自身のもの)は一覧に出さない |
| `DN_SDMIXSET` | 27 `OB_SND_MIXSET` | 書く。`SND_MIX_ALL`で全体の左と右と消音、`SND_MIX_APP`でプログラム(実身のUUID、なければプロセスの番号)の音量と消音 |

書かれた設定は、最後の変更から1秒たつと、サウンドデバイスのタスクが機器の設定の実身に残す(`SOUND_VOL 左 右 消音`の行と、プログラムの実身ごとの`SOUND_APP UUID 音量 消音`の行)。起動時と機器の設定の実身が書き換えられたときに、カーネル(`uconf.c`)がそれを読んでミキサーに入れる。ボリュームを引いている間の細かな変更は1回の書込みにまとまる。

これらの構造体は`INT`と`UINT`で作る。プログラムを`config.h`を先に読まずにビルドすると`W`と`UW`は64ビットになり、カーネルの構造体と大きさが食い違うためである。

試験は`ktest_snd`の`test_mixer`で、2つのプログラムとして扱う2つのチャネルに一定の値(4000と4000、2000と-2000)を鳴らし、ミキサーが出したサンプル(`knl_snd_tap`)で、和(6000と2000)、プログラムの音量50(4分の1)、消音、全体の左だけ50、全体の消音、和が16ビットを超えたときに32767の手前に曲げられること、設定が機器の設定に残り、読み戻されることを確かめる。

ブザーとキーやボタンのクリック音は、音箱にある音の実身(ブザー音、押下音、離し音)をサウンドデバイスで再生したものである。音の実身のレコード1にWAVがあればそれを、なければメタデータにある音の高さと長さから生成した音を再生する。ブザー音の高さで長さだけを変えた短い音(100ミリ秒、`WM_BEEP_TICK`)と長い音(600ミリ秒、`WM_BEEP_LONG`)もあり、画面印刷の秒読みが使う(11.24)。鳴らし方は6.5.5のとおりである。

## 6.6 カメラ

カメラデバイス`cama`は、カメラごとのサブユニット`cama0`から`cama3`(`cama`は`cama0`と同じ)を持つ(`include/ts/cam.h`、`device/cam/cam.c`)。カメラは来た順に空いているユニットに入り、いる間はそのユニットのままである。

| データ番号 | 内容 |
| --- | --- |
| 0 `DN_CAMFRAME` | フレームを読む。そのプログラムがまだ読んでいない一番新しいフレームを、ヘッダ(`T_CAMFRAME`、番号、形式、大きさ、時刻、カメラのPTS)に続けて返す。無ければ0バイト。待たない。サイズ0で読むと、ヘッダを含めた大きさが分かる |
| -1 `DN_CAMINFO` | カメラの状態、VIDとPID、UVCのバージョン、製品名、モードの数、選んだモード |
| -2 `DN_CAMMODES` | モード(`T_CAMMODE`)の一覧。形式(YUY2、NV12、UYVY、MJPEG)、幅と高さ、最大のフレームの大きさ、フレームの間隔 |
| -3 `DN_CAMMODE` | 書くとモードを選び、カメラと取り決めた値(間隔、ペイロードとフレームの大きさ、代替設定)を返す |
| -4 `DN_CAMSTREAM` | `CAM_START`で流し始め、`CAM_STOP`で止める。モードを選ぶ前は`E_OBJ` |
| -5 `DN_CAMSTAT` | 完成したフレーム、捨てたフレーム、プログラムが読んだフレームの数 |

フレームは3つのバッファを回して受け取る。一番新しいフレーム、プログラムがコピーしている最中のもの、次に入れるものである。バッファはカメラのスピンロックの下で選んで目印を付け、ロックの外でコピーする。クラスドライバはUSBの管理タスクのロックを持ったままフレームを渡すが、読む側を待たない。空きの無いときに来たフレームは捨てた数に数える。プログラムごとに最後に読んだフレームの番号を覚え、同じフレームを2度返さない。バッファの大きさは選んだモードの最大のフレームで、モードを選んだとき、流していない間に作る。最後に閉じたプログラムが流れを止める。

UVCのクラスドライバ(`device/usb/uvc.c`)は、VideoControlのインタフェースからUVCのバージョンを、最初のVideoStreamingのインタフェースから形式、フレームの大きさと間隔、アイソクロナスの代替設定と帯域(またはバルクのエンドポイント)を読む。H.264のようなフレームベースの形式は使わない。モードは`VS_PROBE`の`SET_CUR`と`GET_CUR`、続く`VS_COMMIT`で取り決め、取り決めたペイロードの大きさを1サービス間隔のバイト数で賄える一番小さい代替設定を選ぶ。アイソクロナスでは1トランザクションが1ペイロードで、バルクでは短いパケットで終わる転送か、取り決めた大きさに達したところがペイロードの終わりである。ペイロードのヘッダ(FID、EOF、PTS、ERR)を読んで中身を自前のバッファに組み立て、EOFかFIDの切替わりでフレームを閉じる。形式に合う大きさ(YUY2とUYVYは幅×高さ×2、NV12は1.5倍)のもの、MJPEGはJPEGの始まり(`FF D8`)で始まるものだけをカメラデバイスに渡し、誤りのあったもの、大きさの違うもの、バッファに収まらないものは捨てた数に数える。

USBの管理タスクは、ロックを持ったままカメラのドライバを付けたり外したりし、カメラデバイスに通知するのはロックを放した後である(`knl_uvc_notify`)。カメラデバイスの要求は自分のロックを持ったまま管理タスクのロックを取るので、逆の順に取らないためである。去ったカメラのスロットは、カメラデバイスが手放すまで次のカメラに使わない。カメラが流している間、管理タスクはサウンドと同じく4ミリ秒ごとにコントローラを見る。

デバイスの実身(サブタイプ`OB_S_CAMERA`)のレコードは、レコード1がフレーム、2から6が上の表の-1から-5である(8.4)。試験のために、カーネル自身のカメラ(`knl_cam_loopback`、YUY2とMJPEGの64×48。`knl_cam_loopback_formats`で片方だけにもできる)があり、試験が渡したフレームを流す。UVCのクラスドライバは、構成の記述子とペイロードを与えて組立てを確かめるエントリ(`knl_uvc_probe_*`、カーネルの試験のときだけ)で試す。本物のカメラは実機で`test_uvc_board`が確かめる。挿したカメラの形式ごとに一番小さいモードを3秒、一番大きいモードを2秒流し、フレームの数と、大きさ(無圧縮)またはJPEGの始まり(MJPEG)を見る。カメラがなければ飛ばす。

## 6.7 動画の復号器

Raspberry Pi 5のBCM2712には、HEVC(H.265)のMainプロファイルとMain10プロファイルを復号する回路がある。これをデバイスの実身「動画の復号器」(サブタイプ`OB_S_VIDEODEC`、`include/ts/hevc.h`、`device/hevc/hevc.c`)として見せる。QEMUとRaspberry Pi 4には無く、実身も作らない。

復号器はストリームを自分では解析しない。プログラムが解析した結果、つまりシーケンスとピクチャのパラメータ、スライスのヘッダ、参照ピクチャの一覧と、スライスのバイト列(エミュレーション防止バイトを含んだまま)を1枚ごとのジョブとして渡す。復号したピクチャを入れる場所(スロット)と、参照ピクチャがどのスロットにあるかもプログラムが決める。ブラウザはChromiumのH265Decoderに解析と参照の管理を任せ、そのアクセラレータがジョブを組み立てる(14.6.7)。

| レコード | 内容 |
| --- | --- |
| 1 | 書くと1枚を復号する。`T_HEVCJOB`、`T_HEVCSLICE`をスライスの数だけ、スライスのバイト列の順。復号を終えて(または失敗して)から戻る。最大4MB |
| 2 | スロットのピクチャを読む。8ビットはNV12(輝度が幅×高さ、続いてUとVが交互に幅×高さ/2)、10ビットはP010(同じ並びで1サンプル16ビットのリトルエンディアン、10ビットを上に詰め下の6ビットは0)。オフセットの上位32ビットがスロット、下位がバイトの位置 |
| 3 | `T_HEVCCONF`(ピクチャの幅と高さ、ビット深度8か10、スロットの数1から17)。書くとスロットを作り直す |
| 4 | `T_HEVCINFO`(バージョン、クロック、復号した枚数、失敗の数、最後の失敗の状態、最後の1枚にかかった時間) |

扱うのは8ビット(Main)と10ビット(Main10)の4:2:0で輝度と色差のビット深度が等しいもの、1920×1088まで、タイルとWPPを同時に使わないストリームである。ジョブのビット深度は`T_HEVCCONF`のものと同じでなければならない。CTBの大きさは16、32、64のいずれでもよい。

復号器は1枚を2つの段で処理する。

1. 第1段はスライスのバイト列のエントロピー復号(CABAC)で、結果を予測単位(PU)と係数の2つのメモリに書く。この段は、メモリに置いた(レジスタ、値)の対の列、コマンドリストで動かす。リストには、パラメータのレジスタ、文脈変数の初期値(スライスの種類と量子化パラメータから求める)、スケーリングリストの係数、スライスごとのメッセージ(種類、参照とその重み、デブロッキングの指定)、タイルやWPPの行の始まりと終わりの位置を入れる。PUや係数のメモリが足りないと第1段はそう言って止まるので、倍の大きさにして第1段をやり直す。
2. 第2段はPUと係数と参照からピクチャを組み立ててループフィルタをかけ、スロットに書く。レジスタに直接書いて動かす。時間方向の動きベクトルを使うストリームでは、スロットごとに動きベクトルのメモリを持ち、後のピクチャがそれを参照する。

各段の終わりは復号器の割込みコントローラから通知される(SPI 98)。ジョブは実身の書込みの中で1枚ずつ処理し、ミューテックスで他の書込みを待たせる。

復号器が触れるメモリ(コマンドリスト、バイト列、PU、係数、スロット)は、4GB未満の物理的に連続したページ(`KAF_DMA32`)から取る。復号器はアドレスを64バイト単位で受け取る。プロセッサが書いたものは復号器に渡す前にキャッシュから追い出し、復号器が書いたスロットは読む前にキャッシュを無効にする。取ったページはゼロで埋めた直後にキャッシュから追い出し、ダーティな行が後で復号器の書いたピクチャの上に書き戻らないようにする。復号器の前のIOMMU(iommu2)が有効でバイパスでないときはバイパスにする。クロックはファームウェアのクロック11を最大にする。

スロットのピクチャは復号器が書いたまま持つ。128バイト幅の列が並び、輝度は1枚のメモリに各列がピクチャの高さ(8の倍数に切り上げ)の行を、色差はUとVを交互にもう1枚のメモリに各列が半分の高さの行を持つ。8ビットでは列の1行が1バイトのサンプル128個である。10ビットでは列の1行が32ビットのリトルエンディアンのワード32個で、1ワードにサンプル3個をビット0、10、20から置き、上の2ビットは使わない。このため列の幅は96サンプルになり、列の数は幅を96で割って切り上げた数になる。色差のワードはU、V、Uと次のワードのV、U、Vのように交互に続く。列と列の間隔(1列のバイト数)と、第1段・第2段のレジスタの設定は8ビットと同じで、ビット深度はSPSのレジスタと第2段の設定のワード(ビット深度の欄と、8ビットでないことを示すビット)、量子化パラメータの初期値に足すQpBdOffset(6×(ビット深度−8))に表れる。重み付き予測のオフセットは8ビットの値のまま渡し、ビット深度に合わせた拡大は復号器が行う。レコード2の読出しで行の並びのNV12またはP010に直す。

### 6.7.1 実機での確認

QEMUには復号器が無いので、実機の確認を`make HEVCTEST=1`でカーネルに入れる(`kernel/sysdepend/rpi5/hevctest.c`)。起動の20秒後に、`tools/hevc/mkjobs.py`がlibx265で作った小さなストリームのジョブ(`tools/hevc/hevc_jobs.bin`)をカーネルのエントリ(`knl_hevc_conf`、`knl_hevc_decode`、`knl_hevc_picture`)で復号し、ピクチャごとのNV12(10ビットはP010)のハッシュ(FNV-1a)をffmpegの復号の結果と比べて、`hevctest:`の行をコンソールに出す。ストリームは5つで、8ビットが1スライスでCTBが32の64×64、2スライスでWPPを使いCTBが64の320×240、CTBが16の128×96、10ビット(Main10)が1スライスでCTBが32の64×64と、2スライスでWPPを使いCTBが64の208×120である。208×120は輝度も色差も10ビットの列(96サンプル)を3つにまたがり、最後の列が途中で終わる。どれもIピクチャに続くPピクチャで、重み付き予測と時間方向の動きベクトルを含む。期待するハッシュは、`mkjobs.py`がffmpeg(libx265が`yuv420p10le`を受け付けるもの)で同じストリームを`nv12`または`p010le`に復号して求める。`mkjobs.py`はffmpegのビットストリームフィルタ`trace_headers`の出力からジョブを作るので、ブラウザとは別の道でジョブの形を確かめることにもなる。

## 6.8 ドライバの規約

- デバイスに渡すアドレスは物理アドレスである。リニアマッピングの外にあるバッファは、`ConvPhysicalAddress`で連続する区間ごとに物理アドレスを求める(4.6)。デバイスから見たメモリが物理アドレスとずれるとき(RP1、Raspberry Pi 4系のEMMC2とPCIe)は、そのずれを足したバスアドレスを渡し、届かないバッファはDMAのゾーン(`KAF_DMA32`)から取ったバッファを通す。
- キャッシュの書き戻しと無効化、デバイスとの間のバリア、待つループの休みは、`DCacheFlushRange`、`DeviceBarrier`、`SmpWriteBarrier`、`CpuRelax`などのアーキテクチャの層の関数(4.8)で書き、`dsb`や`dc civac`などの命令を直接書かない。
- 割込みハンドラが参照するデータは、割込みを許可する前に用意しておく。
- ドライバ内の排他制御はスピンロックかミューテックスで行う。割込みを禁止するだけでは他のCPUを止められない。
- 期限を過ぎた時刻をコンペアレジスタに残すと割込みが連続して発生するので、設定する前に確認する。

# 第10章　表示とウインドウ

## 10.1 構成

画面まわりは外核の3つの管理機能からなる。描画管理`dp_`、フォント管理`fn_`、ウインドウマネージャ`wm_`である。いずれもEL1で、呼び出したプログラムのコンテキストで実行される。ただし画面の組み立てだけは、ウインドウマネージャの合成タスクが行う(10.4.4)。プロセスからはSVCクラス8と9、それにウインドウの実身の操作(クラス7)で使う。

```text
 プロセス             ウインドウの実身(ob_) / dp_ / wm_・mn_・kc_ のSVC
 ───────────────────────────────────────────
 ウインドウマネージャ  ウインドウ、枠、合成、部品、パネル、メニュー、データボックス、
                      外観設定テーブル、ポインタ、メッセージ行、トレー
 描画管理 dp_        描画環境、塗りつぶし、線、図形、領域、ピクセル転送
 フォント管理 fn_     FreeType。グリフを生成し、描画環境に描く
 画面ドライバ         オフスクリーンバッファとディスプレイへの転送
```

## 10.2 描画

描画はすべて描画環境(番号`gid`)に対して行う。描画環境は、描画先のピクセル、座標の原点、描画可能な範囲(フレームとクリッピング領域)、色、描画モード(上書き、排他的論理和、論理積)を持つ。ウインドウはそれぞれ専用の描画環境とピクセルバッファを持つので、ほかのウインドウに覆われても内容は失われない。

| 分類 | 主な関数 |
| --- | --- |
| 塗りつぶしと線 | `dp_fill_rect`、`dp_frame_rect`、`dp_line`、`dp_line_wide` |
| 図形 | `dp_fill_poly`、`dp_draw_poly`、`dp_fill_round`、`dp_frame_round`、楕円、扇形、弓形、円弧、シード塗りつぶし |
| 領域 | `dp_rgn_*`。行ごとの区間で表した領域 |
| ピクセル | `dp_put_argb`、`dp_get_argb`、`dp_put_mono`、`dp_put_gray` |
| パターン | 2色の網掛け(8段階)か、タイルと透過マスク。図形の`<pattern>`が`masks`で名指すマスクは、その図形の`<mask>`の定義を使い、なければTADの標準のマスク(0〜13番。4×4の模様で、1〜7番は0%から100%までの網、8〜13番は縦線、横線、2方向の斜線、2種の格子)を使う(`outer_kernel/tad/tad_view.c`) |

画像はPNG、JPEG、BMP、GIF、ICOをデコードでき、PNGへのエンコードもできる(`img_`)。

画面そのものは実身「画面」である(8.4)。解像度、色深度、選択できる解像度はそのレコード1で読み、解像度の変更はそこに書く。デスクトップが起動時に機器の設定の解像度にするときも、システム環境設定が解像度を表示するときも、この実身を通す。描画管理とウインドウマネージャは画面ドライバの関数を直接使う。

描画環境は、描いた範囲を通知できる(`dp_set_watch`)。通知する設定にした描画環境が後で画面に重ねるピクセル(ウインドウのピクセル)に描くと、描画管理は描いた矩形を、描画可能な範囲で切った画面座標で、`dp_watch`で登録された1つの関数に渡す。ウインドウマネージャは、すべてのウインドウの描画環境と枠を描く描画環境をこの設定にし、渡された矩形を次の組み立てに加える(10.4.4)。プログラムは`wm_damage`で損傷を通知しなくても、描いた部分が次の`wm_update`で画面に出る。関数は描画管理のロックを持たずに呼ぶ。

画面ドライバ(`device/disp/disp.c`)は、バックバッファのうち変化した部分を`ts_disp_damage`で受け取り、最大16個の別々の矩形として覚えておき、保留(`ts_disp_hold`)が解けたときに矩形ごとにフレームバッファへ送る。重なるか近い2つの矩形は、両方を囲む矩形が2つの面積の和より4096画素以上大きくならなければ1つにまとめる。それより離れていれば、間の画素を送るより別々に送るほうが安い。左上で点滅するキャレットと右下の時計は、画面全体ではなく2つの小さな矩形として送られる。16個を超えたときは、新しい矩形を、まとめたときに増える面積が最も小さい矩形にまとめる。`ts_disp_stat`は、送った回数、矩形の数、行数、画素数、送りにかかった時間の合計、面を切り替えた回数、切り替えが効くのを待った回数とその時間の合計を返す。フレームバッファが2面を持てる画面では、送りは表示していない面に書き、書き終えてからその面を表示させる(10.2.1)。

プロセスは、自分が作成したウインドウの描画環境(`wm_obj_gid`で取得する)にだけ、次の関数で描画できる。

| 関数 | 機能 |
| --- | --- |
| `dp_fill_rect`、`dp_frame_rect`、`dp_line` | 塗りつぶし、枠、線 |
| `dp_put_argb` | ピクセルを書き込む |
| `dp_text`、`dp_text_width` | システムフォントで文字列を描く、幅を求める |
| `dp_draw_tad` | xmlTADを描く |
| `dp_img_decode` | 画像をデコードする |
| `wm_obj_flush` | 描画した内容を画面に反映する |
| `wm_obj_surf`、`wm_obj_put` | 作業領域の面をプロセスの空間にマッピングして得る、面に描いた矩形をウインドウに置いて画面に反映する |

自分で画素を作るプログラム(ブラウザなど)は、描画環境を通さずに作業領域の面(`wm_obj_surf`)に直接描く。面はウインドウごとにカーネルが持つページで、作業領域と同じ幅と高さの画素(1行は幅×4バイト)を持ち、呼んだプロセスの共有メモリ領域(5.3)の新しいアドレスに、読み書きできるようにマッピングする。ページは仮想アドレスだけが連続した領域(`knl_vmap`)なので、1ページずつ物理アドレスを引いてマッピングする(`knl_prc_map_kernel`)。ページはマッピングする前に0で埋める。プロセスは面に描いたあと、変わった矩形(作業領域の座標で最大16個)を`wm_obj_put`で渡す。カーネルは、ウインドウマネージャのロックを持ったままそれらの矩形を面からウインドウのピクセルへ行ごとにコピーし、描画環境で描いた矩形と同じくそのタスクが描いた矩形として記録して、`wm_update`と同じように組み立てを依頼し、終わるまで待つ。

ウインドウのピクセルそのものをプロセスにマッピングしないのは、二つの理由による。合成タスクは組み立てのたびにウインドウのピクセルを読むので、プロセスが直接描くと、ページを塗りつぶして文字をまだ描いていない状態が、ほかの理由で起きた組み立てによって画面に出る。また、ウインドウのピクセルには枠とタイトルバーも含まれるので、プロセスがそれを書き換えられてしまう。面はダブルバッファの裏側に当たり、表側であるウインドウのピクセルへは変わった矩形だけをコピーする。コピーするのはウインドウマネージャのロックの中で、合成タスクは組み立ての間このロックを持っているので、組み立てがコピーしかけのピクセルを読むことはない。コピーする量は変わった矩形の分だけで、`dp_put_argb`のように画素ごとに描画モードと透過色を調べることもない。面の画素の上位バイトは、透過色を使うウインドウ(ポップアップ)では0xFFが透過を表し、ほかのウインドウでは使わない。

ウインドウが持つ面は1つで、最後に求めたプロセスのものである。同じプロセスが同じ大きさのうちに求めると同じ面を返す。ウインドウの大きさが変わっても面はそのまま残り、`wm_obj_put`は面と作業領域の両方に収まる範囲だけをコピーする。プロセスが改めて`wm_obj_surf`を呼ぶと、新しい大きさの面を新しいアドレスに作り、古い面を手放す。手放すときは、先にプロセスの古いアドレスの各ページを何もないページ(書き込みが捨てられるページ。`knl_prc_sink_shared`)に置き換えてTLBを無効にし、そのあとでページを解放する。ウインドウが閉じたとき(`wm_close`)と、プロセスが終了したとき(`knl_wmobj_prc_end`が呼ぶ`knl_wm_surf_prc_end`。自分が作ったのではないウインドウの面も含む)も、同じ順で手放す。プロセスがまだ古いアドレスに描いていても例外にはならず、書き込みは捨てられ、次の`wm_obj_put`は`E_OBJ`か`E_ID`を返す。共有メモリ領域のアドレスは一度しか割り当てないので、終了したプロセスの番号を受け継いだプロセスに古いアドレスのページが見えることはない。

カーネル試験の`prcobj`の組の`test_surf`は、`tests/uprog/svcprog.c`の`SP_SURF`を使って、プロセスが面に描いて置いた色が画面に出ること、同じ大きさのうちは同じ面が返ること、誤った引数(矩形の数、カーネルのアドレス、読出し専用のアドレス)を拒むこと、ウインドウを大きくして求め直すと新しい面が別のアドレスに大きく作られ、古いアドレスがもうそのページを指さないこと、ウインドウを閉じると面のページが解放され、プロセスがなお面に書いても例外にならず`wm_obj_put`を拒まれること、描き続けるプロセスを終了させると面が残らないことを確かめる。ブラウザでの効果は14.7.1で述べる。

### 10.2.1 画面の2面の切り替え

フレームバッファが画面2枚分の行を持ち、どちらを表示するかを画面に指示できるときは、画面ドライバは2面を切り替えて使う(ページフリップ)。送る矩形は表示していない面(裏の面)に書き、すべて書き終えてから裏の面を表示させる。送りかけの面が画面に出ることはない。裏の面は1回前の送りの時点の内容なので、送りのたびに、今回の矩形に前回の矩形を加えて(4096画素の規則で近いものを1つにまとめながら)バックバッファからコピーする。前回の矩形は前回表示させた面にだけ書いてあり、もう一方の面にはないからである。バックバッファには両方の最新の内容がある。

面の切り替えは画面の次の更新から効き、それまでは前に表示していた面が読み出され続ける。そのため、次の送りでその面に書く前に、前回の切り替えが確実に効いたことを確かめる。切り替えから更新1回分の時間が過ぎていれば待たない。過ぎていなければ、垂直帰線を待てる画面では切り替えの後に始まった帰線が終わるまで、待てない画面では切り替えから更新1回分の時間が過ぎるまで待つ。待つのは画面ドライバのロックを持った送りの中で、ウインドウマネージャのロックはすでに放している。どちらかの待ちがある画面では送りが1更新に1回に揃うので、合成タスクは自分では間隔を取らない(10.4.4)。

画面が更新の周期と、最後に帰線の終わりを見た時刻を返せるハードウェア(`T_DISPHW`の`frame_ns`、`blank_ns`、`blank_seen`)では、帰線を時計として使う。最後に見た帰線の終わりから周期ずつ数えて、前の切り替えの後に始まる最初の帰線の終わりを求める。切り替えが帰線の始まりの200マイクロ秒前(`DISP_GUARD_US`)より後なら、その帰線では効かないとみなして次の帰線にする。送りがその時刻を300マイクロ秒(`DISP_BLANK_SLOP_US`)過ぎてから来たときは、切り替えはもう効いているので待たない。画面だけを見て待つと、切り替えのときの値から数えるので、すでに過ぎた帰線は数えられず、次の帰線まで更新1回分余計に待つことになる。時刻より前に来たときは、帰線の始まりの1ミリ秒前(`DISP_WAKE_US`)まで眠り(`tk_dly_tsk_u`)、そこから画面を見て帰線を待つ。帰線を待つたびに見た帰線の終わりで時計を合わせ直すので、時計はずれない。最後に帰線を見てから1秒を過ぎたときは時計を使わず、画面だけを見て待つ。送りが時計で求めた時刻と300マイクロ秒より離れた帰線で終わったときは、時計が外れたものとして数える(10.4.5の`off`)。QEMUの画面には帰線がないので、試験は`knl_disp_sim_blank`で疑似的な更新(周期の1/20の帰線が周期ごとに終わる)を与え、同じ処理を確かめる。

`ts_disp_flip`で切り替えを使うかどうかを変えられる。使い始めるときは、裏の面に画面全体が欠けているものとして、次の送りで画面全体をコピーする。やめるときは、最後に表示させた面に以後の送りを書く。`ts_disp_ref`は、面の数(`fb_pages`)、表示している面(`fb_shown`)、切り替えを使っているか(`flipping`)を返す。解像度を変えると新しい大きさの最初の面を表示し、2面を使い続けられるときは次の送りで裏の面に画面全体をコピーする。機種に依存する層(`T_DISPHW`)は、面の数、面を切り替える関数、垂直帰線を待つ関数(なければ`NULL`)、垂直帰線を待たないときに切り替えが効いたとみなすまでの時間(`latch_us`)、起動時から切り替えを使うかを渡す。

| 機種 | 2面の取り方と切り替え | 起動時 |
| --- | --- | --- |
| Raspberry Pi 5 | メールボックスで仮想の大きさを高さの2倍にしたフレームバッファを求め(`SET_VIRTUAL_WH` 0x00048004)、仮想のオフセット(`SET_VIRTUAL_OFFSET` 0x00048009)の行で表示する面を指示する | 起動時の確認に通れば使う |
| Raspberry Pi 4系 | 1面のまま | 使わない |
| QEMU | `bochs-display`のモードは仮想の高さを2倍にしてあり、Yのオフセットのレジスタで表示する面を指示する。切り替えはすぐに効く | 使わない。試験(`ktest_disp`の`test_flip`と`test_blank`、`ktest_wm`の`test_pace`)だけが使う |

Raspberry Pi 5では、ファームウェアが起動前に用意して`simple-framebuffer`のノードで通知するフレームバッファは1面なので、そのノードの大きさで2面のフレームバッファをメールボックスで求め直し、ノードのバッファは使わなくなる(ノードがないときも2面で求める)。求める前に、バッファを確保しない問い合わせ(`TEST_VIRTUAL_WH` 0x00044004)で2面をくれるかを尋ねるが、その答えは記録に出すだけで、答えが2面に足りなくてもバッファを求める。Raspberry Pi 5のファームウェアは、`config.txt`で上限(`max_framebuffer_width`、`max_framebuffer_height`)を広げても、この問い合わせに今の画面の大きさを答えた。何面をくれるかは、実際に求めたバッファの仮想の大きさで判断する。Raspberry Pi 5のファームウェアは、2面を求めると仮想の高さを2倍と答えるが、新しいバッファは確保せず、起動時からの1面のバッファ(ノードと同じアドレス)をそのまま返し、確保した大きさも1面分と答える。2面目はそのバッファの直後の行から表示されるので、`CNF_DISP_FLIP`のときはページの割当て(`pfalloc.c`)が起動の初めに、ノードのバッファの直後の1面分も予約しておく。この範囲はファームウェアの領域ではなく、カーネルに渡された普通のメモリである。ただし実機(2026年10月3日)では、ファームウェアは表示の位置(`SET_VIRTUAL_OFFSET`)を2面目に変えたと答え、読み返しても2面目と答えたが、画面は1面目を表示したままで、起動時の照合が失敗した。メールボックスで答えた画素の並びも実際の表示には効いておらず、その並びで描くと赤と青が入れ替わった。そのため、Raspberry Pi 5の既定は`DISP_FLIP=0`(ノードの1面)とし、`make DISP_FLIP=1`で試せるだけにしている。試すときも、ファームウェアがノードと同じアドレスを返したら、画素の並びと不透明度の扱いはノードのものを使う。表示の位置を本当に切り替えるには、ファームウェアに任せず、表示のハードウェア(HVS)の表示リストを直接書き換える必要がある。`etc/boot/config.txt`は、4Kの画面の2面まで取れるように上限を3840×4320にしている。メールボックスで求めたバッファは、画素の並びが青を下位にし、最上位のバイトを不透明度として読まない設定(`SET_ALPHA_MODE`で無視)にする。ノードの形式`a8r8g8b8`では最上位のバイトを0xFFにするために1画素ずつ変換して送っていたが、この設定が通れば送りは行ごとのコピーになる。ファームウェアがくれたバッファがカーネルの使っているメモリにかかるなどして使えないときはノードに戻すが、そのときファームウェアはもうノードのバッファを表示していないかもしれない。そのような画面や、2面にすると表示が乱れる画面では、`make DISP_FLIP=0`(`CNF_DISP_FLIP`)でビルドすると、今までどおりノードの1面を使う。

Raspberry Pi 5の今の既定(`rpi5.mk`の`DISP_FLIP=1`)では、面の切り替えをファームウェアに頼まず、表示のハードウェア(HVS)の表示リストを直接書き換えて行う(`disp_rpi5.c`)。起動時にHVSのレジスタのアドレスウインドウから表示リストを探し、ノードのフレームバッファのアドレスを持つワード(実機では2つ)を見つける。2面目は、ページの割当て(`pfalloc.c`)が起動の初めに予約した1面分(`knl_fb_page2`)で、切り替えはそれらのワードに表示する面のアドレスを書くだけである。切り替えが効いたことは、フレームごとに変わるHVSのレジスタで確かめる。起動時に先頭の128ワードを120ミリ秒のあいだ休まずに読み続け、1フレームに1回(120ミリ秒で5〜9回)か2回(11〜17回)変わるワードを選ぶ。実機ではオフセット0x24のワードが1フレームに2回変わった。2回変わるワードは垂直帰線の間だけ別の値を持ち、その間は1080pで1ミリ秒に満たない。そのため垂直帰線を待つ処理も、起動時と同じく休まずに読み続ける。1ミリ秒眠りながら読むと帰線を読み飛ばし、2026年10月5日の実機では最初の待ちで40ミリ秒の上限を超えた。

ワードを選んだ後、さらに150ミリ秒までそのワードを読み続けて、変わった時刻を32回まで記録し、帰線の時計を作る(`hvs_clock_find`)。2回変わるワードでは、長く保つ方の値が帰線の外の値で、その値に変わった時刻が帰線の終わり、もう一方の値の続いた時間が帰線の長さである。1回変わるワードでは、変わった時刻をそのまま帰線の終わりとする。周期は最初と最後の帰線の終わりの間隔を回数で割った値で、どの終わりも最初の終わりから周期の整数倍の1/50以内に並び、周期が5〜50ミリ秒のときだけ時計を使う。ワードが2つより多くの値を取るとき、帰線の終わりが3回に満たないときも使わない。使えれば`hvs: clock: a frame every 〜 us (〜 ends of a blank timed), its blank 〜 us`を出し、切り替えが効いたとみなす時間を周期に1ミリ秒を足した値にする。帰線を待つ処理は、切り替えの後に始まった帰線の終わりを待つ。切り替えが帰線の中で行われたときは、その帰線の終わりは数えず、次の帰線の終わりまで待つ。見た帰線の終わりは時計に渡す。時計がある間は`disp.c`が帰線の1ミリ秒前まで眠らせるので、CPUを占めるのは帰線の前後の1ミリ秒余りだけである。時計が作れなかったときは、今までどおり切り替えのときの値から決まった回数変わるのを待ち、待つのは前の切り替えから更新1回分(17667マイクロ秒)以内に次の送りが来たときだけである。上限を超えたときは、その回は切り替えから17667マイクロ秒が過ぎるまで待つ。3回続けて上限を超えたときだけ、以後は垂直帰線を待たずに時間で待つ(`disp: flip: the wait for the vertical blank failed 3 times in a row`)。

面の切り替えと垂直帰線の待ちは1フレームごとにメールボックスを呼ぶので、`knl_mbox_property_wait`を使う。答えを500マイクロ秒まではそのまま待ち、過ぎると1ミリ秒ごとにタスクを眠らせて見る(上限100ミリ秒)。垂直帰線を待つ間、CPUを更新1回分占めないためである。

起動時の確認は2段からなる。まず`disp_rpi5.c`が、2つ目の面を表示させて表示の先頭の行をファームウェアから読み返し(`GET_VIRTUAL_OFFSET` 0x00040009)、1つ目の面に戻して同じく読み返す。読み返した行が違えば1面に戻す。続けて、垂直帰線まで答えを返さないタグ(0x0004800E)を7回続けて呼び、戻った時刻の間隔を測る。このタグはファームウェアのタグの一覧の文書には見当たらず、Pi 5のファームウェアで働くかは分かっていないので、起動時に測って決める。垂直帰線の割込みは使わない。表示のパイプライン(HVSと画素の出力)はファームウェアが動かしていて、その割込みもファームウェアが受けるからである。カーネルが受けるには、表示の経路を自分で動かすことになる。間隔の中央値が5〜50ミリ秒で、6つの間隔がどれも中央値の±25%に収まるときだけ垂直帰線を待てるものとし、切り替えが効いたとみなす時間を中央値の9/8にする。タグに答えがない、すぐに答える、間隔がそろわないときは使わず、60Hzの更新1回分に1ミリ秒を足した17667マイクロ秒を待つ。面を指示するタグそのものが2回とも4ミリ秒以上かかったときは、ファームウェアが垂直帰線まで待ってから答えているものとし、答えが返った時点で切り替えが効いたとする。

次に`disp.c`が、2面で送った結果を読み返して照合する(`flip_check`)。黒に見える暗い模様をバックバッファに描き、1面で画面全体を送って、表示している面が送ったとおりかを確かめる。次に2面に切り替え、1〜3個の矩形に新しい色を描いて送ることを8回繰り返し、各回で、その回と前の回の矩形の全画素と、無作為に選んだ4行の全画素を表示している面から読んで、送りが変換したバックバッファの値と比べる。最後に表示している面の全体を比べる。面はドライバのキャッシュしないマッピングから読むので、読む値は画面が読む値である。違う画素があれば1面に戻す。この照合で確かめられるのは、2面の大きさ、ピッチ、面の位置と、前回の矩形を加える処理である。画面が指示した面を本当に表示しているかは、ファームウェアが読み返す値でしか確かめられないので、最後は画面を見て確かめる。続けて、画面全体を1面で送る時間と2面で送る時間(コピーの時間、面を指示する時間、前の切り替えが効くのを待った時間)を、それぞれ3回のうち最短で測る。2面の送りは続けて行うので、待つ時間は送りが待ちうる最大の時間に近い。最後に両方の面を黒に戻す。

カーネル試験の`disp`の組の`test_flip`は、QEMUで2面を使い、画面全体を送ると表示する面が替わること、離れた2つの矩形を1つずつ送ると、2つ目の送りで表示した面に1つ目の矩形も入っていること、1〜3個の矩形を保留の中で描いて送ることを20回繰り返し、毎回、表示する面が替わり、その回と前の回の矩形と1行が表示している面でバックバッファと一致すること、切り替えの回数と送りの回数が20ずつ増え、待つことがないこと、使うのをやめると最後に表示した面に送ることを確かめる。同じ組のほかの試験は1面で送った結果を読むので、組の初めに2面をやめ、終わりに元に戻す。

実機の起動では、次の行が出る(数値は例である)。

```text
disp: asking the firmware for a framebuffer of 1920 x 1080, 32 bpp, 2 pages
disp: flip: two pages of 1920 x 1080 at 3e000000; the firmware showed the second from row 1080 in 180 us and the first again in 150 us
disp: vsync: the waits for the blank came every 16667 us (16500 to 16800, 60 Hz); a send within 18750 us of a flip waits for the next blank
TessronOS: display 1920 x 1080, 32 bpp, pitch 7680, at 3e000000, via mailbox, room for two pages
disp: flip: check passed: 8 sends, 2900 Kpx read back from the page shown, all as the back buffer holds them
disp: flip: whole screen 1920 x 1080: one page 2600 us; two pages 2700 us (copy 2550, flip 150, waiting 14000 for the flip before to be taken); waits for the next vertical blank
disp: flip: on: each send goes to the page not shown, which is then shown
```

| 行 | 分かること |
| --- | --- |
| `disp: flip: the firmware would not give two pages` | 問い合わせで断られ、ノードの1面のまま使う(今までと同じ) |
| `disp: the firmware gave one page` | 仮想の大きさが通らなかった。メールボックスの1面で使う |
| `disp: flip: the firmware's new buffer at 〜 cannot be used` | くれたバッファが使えずノードに戻した。画面が出なければ`DISP_FLIP=0` |
| `disp: flip: two pages of 〜` | 2つ目の面への切り替えと戻しが読み返せた。その時間が4ミリ秒以上ならファームウェアが垂直帰線を待って答えている |
| `disp: flip: the firmware does not show the second page` | 読み返しが合わず、1面で使う |
| `disp: vsync: the waits for the blank came every 〜` | 垂直帰線を待てる。周期とその幅 |
| `disp: vsync: no wait for the vertical blank`、`not a refresh apart` | 垂直帰線は待てない。切り替えから17667マイクロ秒を待つ |
| `disp: flip: check passed`、`check FAILED` | 2面の照合の結果。失敗なら最初の違う画素の位置と値が出て1面になる |
| `disp: flip: whole screen 〜` | 画面全体の送りの時間の、1面と2面の比較 |
| `disp: flip: on`、`off` | 以後の送りが2面か1面か |

使用中は、ウインドウマネージャの60秒ごとの統計の行(10.4.2)の末尾に、送りの回数と1回あたりの時間、面の切り替えの回数、切り替えが効くのを待った回数と1回あたりの時間が出る。照合に通っても、画面がちらつく、古い内容と新しい内容が交互に見えるときは、画面が指示した面を表示していない。そのときは`DISP_FLIP=0`でビルドする。

GPUで組み立てた範囲をフレームバッファへ直接書くことはしない。理由は13.10.8で述べる。

描画環境には、画素を持たずに描画を記録する環境もある(`dp_open_rec`)。この環境に描くと、塗りつぶし、枠、線、多角形、太さと線種のある折れ線、角の丸い矩形、画素の転送の各関数は、画素を書かずに、呼び出しを受け手の関数(`T_DPREC`)にそのまま渡す。原点、フレーム、クリッピングは普通の環境と同じに働き、渡すときに切り取りの矩形を1つ添える。上書き以外の描画モードの描画は渡さない。印刷はこの環境でページをPDFの描画命令に変換する(11.22)。

## 10.3 フォント

フォントはFreeTypeで扱う。TrueTypeとOpenType(CFFを含む)を読み込め、グリフはヒンティングをせずに256階調で生成し、線を大きさに応じて少し太らせ、1/4画素の位置で作り分け、背景のピクセルとリニア空間で混ぜて描く(10.3.1)。フォントはシステムボリュームのフォントの実身から読み込む。一度生成したグリフはキャッシュする。縦書きでは、書体のGSUB表の`vert`の機能が示す縦書き用の字形を使い、字を上から下へ字の大きさの枠に1字ずつ置く(`fn_vdraw`、11.21)。

フォントの実身は書体箱からリンクしてあり、実身名かメタデータの`tessronos.file.name`で名前が付いている。書体箱にあるのは、ゴシック体の`NotoSansJP-Regular.otf`、明朝体の`NotoSerifJP-Regular.otf`、等幅の`NotoSansMonoCJKjp-Regular.otf`(Noto Sans Mono CJK JPを、Noto Sans JPと同じ文字の範囲に絞ったもの)の3つである。どれも`etc/font`のファイルから`tools/mkobj.py def`で`etc/def`に実身を作り、ビルドのときに`tools/mkobj.py rec`でファイルをレコード1にする。デスクトップは起動時に書体箱のリンク先をすべて開き、システムのフォントを`ob_fnd_lnk`で名前(`NotoSansJP-Regular.otf`、`NOTOSANS.OTF`の順)から選ぶ。どちらもなければ、最初に開けたフォントを使う。`etc/font/koganei.ttf`は出どころとライセンスが分からないので書体箱に入れず、試験用ディスクの`/boot`にファイルのまま載せて、TrueTypeの字形を読む試験(`ktest_fn`)だけが使う。壁紙も同じように壁紙箱から`TESSRON.PIC`を探し、なければ最初のリンク先を使う。自分で文字を描くプロセスは`ts_face_find`、`ts_face_list`(`include/ts/face.h`)で書体箱からフォントの実身を得る。どちらも箱のリンクを名前で探す`ob_fnd_lnk`、`ob_lst_lnk`(8.3)を使う。

FreeTypeは複数のタスクから同時に呼んではならないので、フォント管理全体を1つのロックで保護する。サイズを設定して文字を描くような一連の操作は、ロックを保持したまま行う。

### 10.3.1 字の描き方

字の描き方は、今のmacOS(10.14以降)と同じ考え方に揃えている。グレースケールのアンチエイリアス、ヒンティングなし、1画素未満の文字送り、線の太らせ、色ごとに分けた描画(RGBのサブピクセルレンダリング)をしないこと、の5点である。

| 項目 | TessronOS | macOS | 以前のTessronOS |
| --- | --- | --- | --- |
| 階調 | 256階調のグレースケール | グレースケール(10.14でRGBのサブピクセルレンダリングをやめた) | 256階調 |
| ヒンティング | しない | しない | しない |
| 混ぜ方 | リニア空間。字の色で曲線を選ぶ | 字の色で決まるガンマで混ぜる | 色の値をそのまま比例で混ぜる |
| 線の太らせ | 大きさの0.0121倍(横)、その1.25倍(縦)、片側0.3画素まで | フォントスムージング(同じ程度の太らせ) | しない |
| 字の位置 | 1/4画素 | 1画素未満 | 1画素 |

#### リニア空間で混ぜる

画面の色の値(sRGB)は光の強さに比例しない。光の強さを表すリニア値は、およそ色の値の2.2乗である。字が画素を半分覆うとき、色の値をそのまま半分ずつ混ぜると、白地の黒い字の縁はリニア値では4分の1ほどの暗さになり、黒地の白い字の縁は4分の1ほどの明るさにしかならない。同じ形の字が、黒字では太く重く、白字では細く見える。

そこで描画管理(`dp.c`の`gray_run`)は、背景と字の色のRGBの値をそれぞれ表(`dp_lin`、16ビットのリニア値)でリニア値にし、覆う割合で混ぜ、表(`dp_inv`と`dp_mid`)で一番近い色の値に戻す。戻す表はリニア値の16分の1ごとの値と、隣り合う値のリニア値の中間を持ち、中間と比べて最も近い値を選ぶ。どちらの表も、その曲線を初めて使うときに作る(1曲線あたり5KB)。表は`outer_kernel/dp/dp_gamma.h`にあり、曲線は7本である。字の色の明るさ(Rec.709の重み)が0の黒ではsRGBの変換式そのもの、明るくなるにつれて2.0、1.8…1.2乗とまっすぐに近づき、白では1乗(色の値をそのまま混ぜる)になる。

字の色で曲線を変えるのは、同じ形でも明るい字は暗い背景の上で線がにじんで太く見えるからである。macOSのCore Graphicsも、黒い字はガンマ2.0、白い字は1.0で混ぜている。Skiaはこれを、字の色の明るさを半分に見なしてマスクのガンマを選ぶことで真似ている。TessronOSは背景の画素を実際に読んで混ぜるので、Skiaのように背景を推定する必要はない。

コントラストの補正(覆う割合そのものを濃くする補正)はしない。SkiaはWindowsとLinuxではコントラストを足すが、macOSではCore Graphicsが字を太らせるのでコントラストを0にしている。TessronOSも太らせ(下記)で重さを戻すので、補正はせず、縁のなめらかさを覆う割合のまま保つ。

混ぜるのは覆う割合が1〜254の画素だけで、0は触らず、255は字の色にする。背景が字の色と同じ値なら変えない。続く画素が同じ背景と同じ割合なら、前の画素の結果を使う。

#### 線の太らせ

リニア空間で混ぜると、縁の画素が明るくなり、メニューや本文の大きさ(線が1〜2画素)では字が細く薄く見える。macOSはフォントスムージングとして、字の輪郭を大きさに応じて外へ広げてこれを補う。TessronOSも同じように、画素にする前の輪郭を`FT_Outline_EmboldenXY`で広げる(`fn.c`の`darken`)。広げる量は片側で、横が大きさ(画素)の0.0121倍、縦がその1.25倍、上限は0.3画素で、72画素を超える大きさでは広げない。16画素では片側0.19画素、全体で約0.39画素太くなる。送り幅は変えないので、字の位置と行の組みは変わらない。

FreeTypeにも線の太らせ(stem darkening)はあるが、使わない。CFFの太らせはAdobeのエンジンの中で行い、線の幅が細いほど多く太らせる(0.5画素以下で0.4画素、1画素で0.275画素、2.333画素以上で0)。ヒンティングをしないときは単位の大きさで輪郭を作るので、太らせる量が大きさに合わない。TrueTypeのドライバには太らせがなく、自動ヒンターの太らせは試験的で、ヒンティングを前提にしている。輪郭を広げる方法なら、CFFとTrueTypeの書体を同じに扱え、ヒンティングもいらない。

太字(`FN_ST_BOLD`)、斜体、回転した字も同じ処理で256階調にする。以前はこれらを白黒の2値で描いていた。書体が持つ埋め込みのビットマップを使う字(太字、斜体、回転でないとき)は、そのまま描き、太らせも1/4画素の作り分けもしない。

#### ヒンティングはしない

ヒンティングは、PostScriptの輪郭の書体では字を作る仕事の大半を占め、線を最大で半画素動かす。1/4画素の位置で字を作り分けても、ヒンティングで線が画素の格子に寄せられると、その効果が消える。ヒンティングをしなければ、字はどの位置でも同じ形になる。

#### 1画素未満の文字送り

文字列を描くとき(`fn.c`の`walk`)、ペンの位置を1/64画素の単位で持ち、字ごとに書体の送り幅(`FT_Get_Advance`、丸めない値)だけ進める。字は、ペンの位置に最も近い1/4画素の位置に置く。1/4画素ずつずれた字は、輪郭をその分ずらしてから画素にしたもので、同じ画素を1画素ずらして置いたものではない。

キャッシュは字ごとの項目(送り幅、上下の高さ)に、4つの位置ごとの画素(`GPIX`)を持つ。測るだけのときは画素を作らない。和文は1字ずつ整数の位置に置くことが多いので、位置0の画素だけで済むことが多い。

字の幅を測る関数(`fn_width`、`fn_fit`、`fn_draw`の戻り値)は、1/64画素のペンの位置を最も近い画素に丸めて返す。文字列の先頭k字の幅は、k字目が置かれる位置と半画素以内で一致するので、文章の組み(`docview.c`)が先頭からの幅で求めるカーソルの位置と選択の範囲は、描いた字とずれない。`fn_fit`は、丸めた幅が与えた幅に収まる最も長い先頭を返すので、`fn_width`の値をそのまま渡せば全体が収まる。丸めは文字列ごとなので、1字ずつ測った幅の和と、まとめて測った幅は1画素以上違うことがある。字間を空けて組む文字列(`run_space`が0でない)は、`docview.c`が1字ずつ整数の位置に描くので、測るときも1字ずつ測って足す。カーニングは以前から使っていない。

縦書き(`fn_vdraw`)では、字を字の枠の中央に置く横の位置を1/4画素で決め、縦は字の大きさの枠ごとに進める。印刷(記録の描画環境)には、ペンの位置を1/65536画素の行列で渡す。

ブラウザはSkiaで自分で字を描き、書体箱から書体の実身を得る(`ts_face_find`)だけなので、ここで述べた描き方の影響は受けない。

#### 速さとキャッシュの大きさ

`fn_report`は、求めた字の数、キャッシュにあった数、画素を作った数、描いた数、FreeTypeと描画にかかった時間に加えて、キャッシュにある字の数、位置ごとの画素の数、画素が使っているメモリと上限(4MB)を出す。カーネル試験`tv`の`test_doc`(見本の文章1ページ、Noto Sans JP)で、変える前と後を測った値は次のとおりである(QEMU、2026年10月15日)。

| 項目 | 変える前 | 変えた後 |
| --- | --- | --- |
| 測る(`tv_doc_height`) | 19ms | 17ms |
| 描く(1回目) | 148ms | 144ms |
| 描く(2回目) | 50ms | 46ms |
| 画素を混ぜる時間の合計 | 27ms | 27ms |
| キャッシュ | (数えていなかった) | 473字、画素は300組で57KB |
| 字の表(4096字分の項目) | 約384KB | 約320KB |

リニア空間で混ぜる処理は表を引くだけで、混ぜるのは縁の画素だけなので、描く時間は変わらない。和文は1字ずつ整数の位置に置くので、画素の組は字の数より少ない。

カーネル試験`fn`の`test_blend`は、白地に黒で半分覆った画素が187前後(リニア値で半分)、黒地に白で半分覆った画素が128、覆わない画素と背景と同じ色の字は元の値、全部覆う画素は字の色になることを確かめる。`test_subpixel`は、13画素の英文で、先頭からの幅が減らないこと、先頭の幅を`fn_fit`に渡すとその先頭が収まること、全体の幅が最後の先頭の幅と同じで、描いた戻り値とも同じことを確かめる。試験用のTrueTypeの書体では、41字の幅は全体で286画素、1字ずつ丸めて足すと303画素で、字ごとに丸めていた以前は文が6%広がっていた。

### 書体の登録と使用

書体箱のフォントの実身1つには、フォントのファイルが1つ入る。TrueTypeのコレクション(`ttcf`)なら1つのファイルに複数の書体があり、0から数える番号で区別する。各書体をどう登録したかは、その実身のリソース`_0_font.json`(`DT_FONT_RES`)にJSONで持つ。リソースの名前は、TSFSの実身がリソースを「_レコード番号_名前.拡張子」の形で持つことに合わせた。

```json
{"faces":[{"index":0,"name":"詳細名","use":true,"family":"Noto Sans JP",
           "class":"0050","attr":"0010","base":""}]}
```

| 項目 | 意味 |
| --- | --- |
| `index` | ファイルの中の書体の番号 |
| `name` | 詳細名。システム環境設定の一覧に出す名前 |
| `use` | 使用するかどうか |
| `family` | 文章が書体を名指すときのファミリ名。空ならファイルの名前表のファミリ名 |
| `class` | フォントクラス(16ビット、4桁の16進数)。各ビットは字の見た目を表す。0x8000見出し用、0x4000と0x2000線の端に飾り、0x1000線の太さに抑揚、0x0800線の端が丸い、0x0400角が丸い、0x0200線が途切れる、0x0100手書き風、0x0080上品、0x0040簡素、0x0020現代的、0x0010和風、下位4ビットは大きさと太さによる読みやすさ |
| `attr` | 属性(4桁の16進数)。0x0001太字、0x0002斜体、0x0004袋文字、0x0008影付文字、0x0010比例(字の幅が字ごとに違う)、0x0020縦書き(縦書き用の字形を持つ) |
| `base` | ベースのファミリ名。この書体にない字を描くファミリ |

リソースに書かれていない書体は、ファイルの最初の書体(番号0)を、ファイルに書かれたとおりのファミリで使う。システムの3つの書体はリソースを持たない。

デスクトップは起動時と書体の登録や変更のたびに`dt_res_faces`で書体箱を読み直す。まだ開いていない書体を`fn_open_obj`で開き、登録の内容を`fn_set_reg`でフォント管理に渡す。開いた書体は、ウインドウやメニューが描くのに使っているかもしれないので、閉じない。使用しないにした書体と、書体箱から外した書体は、開いたまま`FN_USE_OFF`にする。この書体は名前でも種類でも見つからなくなり、`fn_nface`の数にも入らない。メモリは次の起動まで残る。フォント管理が同時に開ける書体は16である。

フォント管理は書体を次のように選ぶ(`fn_find_style`)。

- 文章の書体名(`<font face>`)と同じファミリの、使用する書体を探す。ファミリ名は、登録したファミリがあればそれ、なければファイルのファミリ名で比べる。
- 同じファミリに複数あれば、求める字の見た目(太字、斜体、袋文字、影付文字)に最も近い属性の書体を選ぶ。求めた見た目を持つ属性は加点し、求めていない見た目を持つ属性はそれより大きく減点する。
- 選んだ書体が属性として持つ見た目は、文章の組版(`docview.c`の`run_font`、`draw_text_item`)で重ねて加えない。太字の書体を太字で求めたとき、さらに太らせることはない。
- 一般名(`serif`、`明朝`、`sans-serif`、`ゴシック`)は、クラスを登録した書体ではクラスの0x6000(線の端の飾り)の有無で、登録していない書体ではファミリ名の語(`Serif`、`Mincho`、`Sans`、`Gothic`)で選ぶ。`monospace`はファミリ名の`Mono`で選ぶ。
- 何も見つからなければシステムの書体を使う。

ベースのファミリを登録した書体にない字は、その字を持つベースの書体で描く(`fn.c`の`letter_face`)。ベースの書体には、元の書体と同じ大きさ、見た目、回転を1回の文字列の描画の間だけ設定し、終わったら戻す。ベースの書体はシステムの書体であることが多く、その設定を変えたままにしないためである。ベースは1段だけで、ベースのベースはたどらない。

見本を表示するときだけ、使用しない書体や登録していない書体を、別の書体として開く(`FN_USE_TRIAL`)。ファミリ名は`見本:実身のUUID:番号`で、この名前を名指したときだけ見つかる。見本のウインドウを閉じると閉じる。

カーネルの試験`ktest_fn`の`test_reg`は、同じファミリの普通の書体と太字の書体から求める見た目に合う方が選ばれ、持っている見た目が答えられること、使用しない書体が名前でも数でも見つからないこと、見本の書体がその名前でだけ見つかること、ASCIIの40字ほどしか持たない試験用のTrueTypeの書体にベースとしてシステムの書体を登録すると、漢字がシステムの書体と同じ幅で描かれ、書体が持つ字はその書体のままで、システムの書体の大きさが元に戻ることを確かめる。

描く先が記録の描画環境のときは、文字をグリフの画素にせず、グリフの番号、元の文字、サイズと、グリフの座標から描く先の座標への行列(長体、平体、斜体、文字の回転を含む)を渡す(`dp_rec_glyph`)。印刷が書体の部分集合を作るために、フォントの表をそのまま読む関数(`fn_sfnt_table`)もある(11.22)。

## 10.4 ウインドウ

ウインドウは、外形、ワークエリア、タイトルバー、スクロールバー、重なり順を持つ。ウインドウの枠とタイトルバーはウインドウマネージャが描き、ワークエリアの中はそのウインドウのプログラムが描く。タイトルバーの左端には、ウインドウが表示している実身のアイコンを表示する。プロセスの小物のウインドウには、そのプログラムの実身のアイコンが表示される。どちらのアイコンも持たないウインドウ(デスクトップのパネルや、アイコンの無いプログラムのウインドウ)には、既定のアイコンとしてシステム環境設定のプログラムの歯車のアイコンを色付きで表示する(`wm_set_icon_default`)。既定のアイコンはデスクトップが起動時に実身から読んで渡す。ウインドウマネージャが枠を描く最中に実身を読まないのは、ウインドウマネージャのロックを持ったまま実身の管理を待たないためである。デスクトップが起動するまでの短い間だけは、タイトルの文字の色で描く図形のマークが出る。

ウインドウの外観は超漢字Vに合わせてある。枠とタイトルバーの図柄は外観設定テーブルの配色で決まり、その上に重ねる見た目(枠やウインドウ全体の半透明、枠とタイトルバーに重ねる色、角の丸み、影、透けて見える背後のぼかし、開閉の動き)はシステム環境設定の〈ウィンドウ〉で設定する(10.4.1)。壁紙は並べて表示、中央、拡大を選べる。

操作の規則は次のとおりである。

- タイトルバーをドラッグするとウインドウが移動する。右下の角をドラッグするとサイズが変わる。移動中の表示を枠線だけにしたとき(`LK_LIVE`が0)は、ドラッグの間は枠線だけがポインタに従い、ボタンを離した位置へウインドウが移動する。
- 仮身や図形をドラッグするときも同じ設定に従う。`LK_LIVE`が1なら、デスクトップはドラッグを始めるときに運ぶものの画面上の位置を`wm_set_drag_from`で渡し、ウインドウマネージャはその部分の画素をコピーして、ドラッグの間は枠線の代わりにその絵をポインタに合わせて動かす。絵は枠線と同じく、どのウインドウよりも上に重ね、どのウインドウの画素にも書かない。大きさを変える操作、範囲の選択、文字列のドラッグ、画面印刷の範囲の指定は、設定によらず枠線で示す。コピーする画素は合計で4M画素(`WM_DRAG_PX_MAX`)までで、それを超える分と画面からはみ出すものは枠線で示す。
- タイトルバー左端のピクトグラムをダブルクリックすると、ウインドウを閉じる。
- ウインドウを閉じると、残ったウインドウのうち最前面のものに入力フォーカスが移る。
- ホイールの縦と横の回転は、ポインタの下にあるウインドウのプログラムにイベントとして通知される。
- 右ボタンで、入力フォーカスを持つウインドウのメニューが開く。ウインドウのない場所で押したときは、最前面のウインドウのメニューが開く。メニューの項目は左ボタンでだけ選び、右ボタンを押しても離しても項目は選ばれない。メニューの外を押すか、Escで閉じる。メニューが開いている間、ポインタとキーの入力はメニューだけに渡し、下のウインドウやパネルには通知しない。パネルの部品は左ボタンだけで操作し、右ボタンの押下では選択を変えない。どのウインドウのメニューも、先頭はウインドウの共通メニュー(閉じる)、末尾はウインドウ、小物、実行である。デスクトップのウインドウは実身の共通メニューで、プロセスとして動くプログラムと管理情報のウインドウはウインドウの末尾の共通メニュー(`SYSDEF_MENU_TAIL`)を取り込む。プロセスのメニューの小物の一覧はカーネルがデスクトップから受け取って埋め、選ばれた小物はデスクトップが起動する。プロセスのウインドウには仮身がないので、実行は灰色で表示する。
- Shift+PauseとCtrl+Shift+Pauseはどのウインドウにも渡さない。入力の層がリングに入れる前に強制終了のタスクへ渡し(`knl_fq_input`)、`wm_read_event`には来ない(5.5.1)。強制終了のウインドウが開いている間は、ほかのイベントもすべてそこへ渡す(5.5.3)。`wm_read_event`は、デスクトップの主ループの監視に入力を待っている間であることを通知する(`knl_wdog_idle`、4.7.2)。

ウインドウは実身としても扱える(ウインドウの実身、8.1)。プロセスは`ob_cre_obj`でウインドウを作成し、キーを開き、イベント通知を要求して入力を受け取る。ウインドウの実身のレコードは次のとおりである。

| レコード | 内容 |
| --- | --- |
| 0　描画 | xmlTAD。書き込むとウインドウの内容がそのTADになる |
| 1　形状 | ウインドウの形を表すxmlTADの図形 |
| 2　配置 | 外形、ワークエリア、重なり順、表示の有無。書き込むとウインドウが移動する |
| 3　状態 | 部品の値 |
| 4以降 | ウインドウの種類ごとのデータ。ウインドウではレコード4がドロップされた仮身、レコード5がスクロールバー、パネルではその部品へのリンク、メニューでは項目 |

ウインドウの作成時のメタデータに、`"rect":[左,上,右,下]`、`"attr":枠の種類`、`"shows":"UUID"`(表示している実身)、`"icon":"UUID"`(アイコンを借りる実身)、`"sub":"UUID"`(親のウインドウ)を指定できる。

`"attr"`に`WM_ATTR_NOFOCUS`を含めたウインドウは入力の対象にならない。`wm_focus`はこのウインドウに入力の対象を与えず、押されて前に出ても、キーはそれまで入力の対象だったウインドウに届く。画面キーボード(キー配列、11.15)はこの属性で作り、絵のキーを`wm_key_put`で入力の対象のウインドウに入れ、キーボードで押されているキーを`OB_N_KEYSEEN`の通知で知る。

`"attr"`に`WM_ATTR_FLOAT`(0x0400)を含めたウインドウは浮かぶ。枠と入力は普通のウインドウと同じであるが、浮かばないウインドウのすべてより前にあり、ポップアップよりは後ろにある。新しく開いたウインドウや前に出したウインドウは、浮かぶウインドウの後ろに来る。浮かぶウインドウどうしの順は、前に出した順である。ブラウザのピクチャインピクチャのウインドウ(14.7.8)はこの属性で作る。

`"attr"`に右(`WM_ATTR_RBAR`)、下(`WM_ATTR_BBAR`)、左(`WM_ATTR_LBAR`)のスクロールバーを含めると、そのウインドウはスクロールバーを持つ。スクロールバーのレコード(`OB_WR_BARS`)は、右、下、左の順に並んだ`T_OBWBAR`で、それぞれ全体の範囲(`lo`〜`hi`)と、そのうちワークエリアが表示している範囲(`clo`〜`chi`)を持つ。単位はプログラムが決める。プログラムはスクロールするたびにこのレコードを書き、つまみの位置と長さを合わせる。書かれたスクロールバーは、ウインドウマネージャがその場で枠に描き直し、ワークエリアが描き直されていなくても次の画面の更新で画面に出す。タイトルとアイコンを変えたときも同じである。スクロールバーの操作はデスクトップが受け取る。つまみの前後の領域を押すと1画面分、つまみをドラッグするとその位置へのスクロールを、`OB_E_SCROLL`でプログラムに通知する。通知の`code`はどのスクロールバーか(`OB_BAR_*`)、`x`は表示範囲の先頭の移動先(範囲内に収めた値)、`y`は操作の種類(`OB_SCR_PAGE`、ドラッグ中の`OB_SCR_KNOB`、離したときの`OB_SCR_DONE`)である。ドラッグ中の通知は外観設定テーブルの`LK_SCR_LIVE`(ドラッグ中にページを追従させる)が1のときだけ送り、つまみそのものはデスクトップが動かす。スクロールバーの上でのボタンの押下はプログラムにも`OB_E_PRESS`として届くが、位置がワークエリアの外になるので区別できる。

`"sub"`を指定したウインドウは従属ウインドウになる。ウインドウマネージャは、どのウインドウを前面に出したり背面に回したりしても、従属ウインドウを常に親のウインドウのすぐ前に置く(`wm_set_parent`)。親のウインドウを移動すると、従属ウインドウも同じだけ移動する(大きさだけを変えたときは動かさない)。移動先が画面の上端より上になる従属ウインドウは上端で止める。従属ウインドウを前面に出すと、親のウインドウも一緒に前面に出て、従属ウインドウはそのすぐ前に来る。親が閉じると、従属ウインドウは独立したウインドウに戻る。タイトルバーのない従属ウインドウも、クリックすると前面に出て入力フォーカスを受け取り、枠をドラッグして移動できる。ブラウザのツールパネル(14.7)、基本表計算の操作パネル(11.13)、基本図形編集の道具パネルと実寸パネル(11.3)がこれを使う。

従属ウインドウは、親のウインドウとそれに従属するウインドウの組(親をさかのぼった先の、どれにも従属しないウインドウを根とする組)が使われている間だけ表示する。

- 使われている組は、最前面(アクティブ)のウインドウの組である。最前面のウインドウは、表示しているウインドウのうち、タイトルバーを持つか従属ウインドウであるもので、いちばん手前のもの(`active_root`)とする。ポップアップ(メニュー、問い合わせのパネル)は開いたウインドウの上に出るものなので数えず、問い合わせに答えている間もその下の組の従属ウインドウは消えない。入力の対象にならないウインドウ(`WM_ATTR_NOFOCUS`、画面キーボード)も数えない。浮かぶウインドウ(`WM_ATTR_FLOAT`、ピクチャインピクチャ)は、どのウインドウで作業していても前にあるので、入力フォーカスを持つときだけ数える。タイトルバーも親もない枠だけのウインドウ(基本図形編集のパレット)も数えない。
- ほかのアプリのウインドウを押して前に出したり、プログラムが新しいウインドウを開いたり(開いたウインドウは最前面に出る)して最前面の組が変わると、ウインドウマネージャはそれまでの組の従属ウインドウを隠す(`subs_away`)。隠しても重なり順の中の位置はそのままで、親のすぐ前にある。
- 親のウインドウ(またはその従属ウインドウ)を押すと、隠していた従属ウインドウを表示する。押したウインドウは前面に出るので(`wm_raise`は従属ウインドウなら親を出す)、親とその従属ウインドウの組がそろって最前面になり、従属ウインドウは親のすぐ前に来る。前に出たウインドウを閉じて親の組が最前面に戻ったときも同じである。1つの親に従属ウインドウが複数あるときは、その間の順は変えない。
- 判定は、重なり順と表示を変えるすべての呼び出し(`wm_open`、`wm_raise`、`wm_lower`、`wm_focus`、`wm_set_parent`、`wm_show`、`wm_close`)の最後に、ウインドウマネージャのロックの中で行う。デスクトップのウインドウにもプロセスのウインドウ(`"sub"`で作った従属ウインドウ)にも同じ決まりが働く。

どのウインドウを隠すかは次のとおりである。

| ウインドウ | 他の組が使われている間 |
| --- | --- |
| 従属ウインドウ(道具パネル、操作パネル、実寸パネル、ブラウザのツールパネル) | 隠す |
| モードレスのダイアログを従属ウインドウにしたもの | 隠す(親の組に戻れば同じ場所に出る) |
| ポップアップ(`WM_ATTR_POPUP`。メニュー、問い合わせのパネル、部品のリスト) | 隠さない。答えるまでの短い間だけ出ていて、ほかのウインドウより前にある |
| 画面の中央に出るパネル(`wm_panel_open_centre`、モーダル) | 隠さない。従属ウインドウではない |
| 基本図形編集のパレット | 隠さない。枠だけのウインドウで、開いている間はそのウインドウだけでイベントを読む(モーダル)ので、ほかの組に移ることがない |
| 基本図形編集のパターン編集 | 図形のウインドウの従属ウインドウにする。モーダルで、開いている間に組が変わることはない。図形のウインドウが最前面のままなので、道具パネルも消えない |
| 独立のウインドウ、浮かぶウインドウ(`WM_ATTR_FLOAT`) | 隠さない |

隠している間の扱いは次のように決めた。

- プログラムから見た表示の有無は変えない。`wm_ref`の`visible`は表示していることを返し、隠していることは`away`で分かる。ウインドウの実身の配置のレコード(`OB_WR_PLACE`)の表示の有無も同じで、プログラムが配置を読んで書き戻しても、隠したままの状態にならない。プログラムが`wm_show`で隠したウインドウは、組が使われるようになっても隠したままである。他の組が使われている間にプログラムが表示を求めたときは、組が使われるようになるまで隠しておく。
- 隠している間は、押しても当たらず(`wm_at`)、画面の合成にも入らない。
- 親のウインドウが閉じられたら、従属ウインドウは独立したウインドウに戻り(親の番号を消す。後で同じ番号で開いたウインドウの従属ウインドウにならない)、隠していたなら表示する。プログラムが閉じ忘れたウインドウが、見えないまま残らないためである。デスクトップの道具パネルは、残っている図形のウインドウにすぐ付け替える(11.3)。
- 隠れている従属ウインドウをアプリが閉じたときは、普通に閉じる。画面に出ていないので描き直しも起きない。
- ウインドウの一覧(右ボタンのメニューの「ウインドウ」、`wm_list`)には、表示している従属ウインドウだけが出る。隠している間は出ない。親のウインドウを選べば組が戻る。ウインドウ一覧の小物はデスクトップの実身のウインドウだけを並べるので、従属ウインドウはもともと出ない。強制終了の小物は、入力フォーカスを持つウインドウとその前のポップアップを見るので、隠れている従属ウインドウは出ない。プロセスを選んで終わらせると、隠れているウインドウも一緒に閉じる(5.5)。
- 画面印刷の「最前面のウインドウ」(`wm_front_group`)は表示しているウインドウだけを組に入れる。組が使われていれば従属ウインドウは表示しているので、親と一緒に取り込む。

ほかのシステムとの比較は次のとおりである。

- Windowsの所有されたウインドウ(owned window)は、所有者より常に前にあり、所有者を前に出すと一緒に前に出て、所有者を最小化すると隠れる。所有者のアプリが非アクティブになっても隠れず、ほかのアプリのウインドウの下に見えたまま残る。前後の関係(親のすぐ前、親を前に出すと一緒に出る)はこれと同じにした。
- macOSのパネル(NSPanel)は、`hidesOnDeactivate`が真(ユーティリティのフローティングパネルの既定)だと、アプリが非アクティブになると隠れ、アクティブに戻ると現れる。隠す決まりはこれに近い。違いは単位で、macOSはアプリ単位であるが、TessronOSは親のウインドウの組の単位である。TessronOSのデスクトップは1つのタスクの中で多くのアプリ(キャビネット、基本文章編集、基本図形編集など)のウインドウを開くので、プロセスやタスクではアプリを区別できない。基本図形編集の別の図形のウインドウに移ったときは、道具パネルをそのウインドウに付け替えるので消えない(11.3)。
- 超漢字の取扱説明書は、基本図形編集の道具パネルを表示メニューの「道具パネル表示」で出したり消したりするもので、表示の状態と位置は実身に保存されると説明している。実寸パネルも同じである。パネルはその実身のウインドウのためのもので、ほかのアプリが前に出たときにどう見えるかは書かれていない。ほかのアプリが使われている間に隠すことは、利用者の指示による決まりで、説明書の記述とは食い違わない(表示メニューで消した道具パネルは、組が戻っても出ない)。

ウインドウはそれを作ったプロセスを記録していて、プロセスが終了するとシステムが閉じる(5.5)。

ウインドウの枠は、ウインドウマネージャが持つ1つの描画環境を、描くたびにそのウインドウのピクセルに向けて描く。枠を描くのはウインドウを開いたり動かしたりしたタスク(プロセスのタスクのこともある)である。この描画環境は専用のロックで守り、向け先の設定から描き終わるまでを1つの操作にする。守らないと、2つのタスクが同時に枠を描いたとき、一方の向け先に他方の範囲で描き、ウインドウのピクセルの末尾を越えて書き込む。ロックの順序はウインドウマネージャのロック(`wm_mtxid`)が先である。ポインタはこの描画環境を使わず、ウインドウマネージャのロックの中でバックバッファに直接置く(10.4.3)。

試験が画面をコピーするときは`wm_copy_screen`を使う。ウインドウマネージャの排他の中で画面全体をコピーするので、画面を組み立て直している途中の状態はコピーされない。画面の一部をコピーするときは`wm_grab_screen`を使う。同じ排他の中で矩形をコピーし、ポインタを除くときは、ポインタを置いたときに取っておいたその下の画素でポインタの部分を置き換える。画面印刷(11.24)がこれを使う。

### 10.4.1 ウインドウの見た目と合成

画面はオフスクリーンバッファの中で、背景から奥のウインドウの順に組み立てる。ウインドウはそれぞれ自分のピクセルバッファを持つので、手前のウインドウを透かして奥を見せるときも、奥のウインドウのプログラムに描き直しを求めない。組み立ては変化した部分だけで行う。変化した部分は1つの外接矩形にはまとめず、最大16個の別々の矩形(部分)として集め、部分ごとに組み立ててそれぞれ画面に送る。重なるか近い2つの部分は、両方を囲む矩形が2つの面積の和より8192画素以上大きくならなければ1つにまとめる。部分を1つ組み立てるたびにウインドウの並びをたどる手間がかかるので、小さな隙間はまとめて組み立てたほうが安い。16個を超えたときは、新しい部分を、まとめたときに増える面積が最も小さい部分にまとめる。部分どうしは重なってもよい。どの部分も背景から組み立て直すので、2つの部分に含まれる画素は2度組み立てても同じ値になる。`wm_update`は、ウインドウごとの損傷(`wm_damage`)と、ウインドウの開閉、移動、前後の入れ替え、不透明度と色の変更、枠の描き直しで変わった場所(影の届く範囲を含む)と、ウインドウの描画環境で描いた矩形(10.2)をこうして集め、ポインタはそのあとで動かす(10.4.3)。外観の設定、配色、壁紙を変えたときは画面全体を変わった場所に加えるので、そのあとの`wm_update`は画面全体を組み立てる。ドラッグ中の枠線(`wm_set_drag`)を動かしたときは、前後の枠線の4辺だけを部分にするので、枠線の内側は組み立て直さない。

見た目の設定は外観設定テーブルの9100〜9116で、枠かタイトルバーを持つウインドウにだけ掛かる。メニューやポップアップの一覧は自分で影を描き、透過させないので対象外である。設定を変えると、開いているすべてのウインドウにすぐ反映される。

既定値では不透明で、角も影もない。プログラムが`wm_set_opacity`で自分のウインドウに設定した不透明度と`wm_set_tint`の色は、この設定とは別に掛かる。不透明度は両者の積になる。

1つのウインドウは次の段階で重ねる(`outer_kernel/wm/compose.c`)。各段階は、ウインドウの外形、ワークエリア、ピクセル、部分ごとの不透明度、角の半径、重ねる色、影、ぼかしをまとめた記述(`T_CPWIN`)だけを入力とし、ウインドウマネージャの内部の表は参照しない。GPUで合成するとき(10.4.2)は、同じ記述を受け取って同じ段階をGPUで行う。

1. 影。外形を影のずれだけ動かした角丸の矩形の内側を最も濃くし、外側では影の幅にかけて直線的に薄くする。ウインドウ自身の下には影を落とさない。半透明の枠から自分の影が透けて見えないようにするためで、覆われる部分は計算もしないので、手間は影の帯の分だけである。濃さは、角丸の矩形の直線部分からの横と縦の距離だけで決まり、どちらかが角の半径と影の幅の和に達すれば0になる。そこで影を落とすたびに、その範囲の距離の組ごとの濃さの表(最大65×65)を先に作り、画素ごとには表を引く。画素ごとに平方根を求めていたときと結果は画素ごとに一致する(`ktest_wm`の`test_shadow_same`が300個のウインドウの外側の全画素で確かめる)。
2. ぼかし。不透明度が255未満の部分について、その下に見える画面(それまでに重ねた背景と奥のウインドウ)をぼかす。ぼかすのは透ける部分だけで、不透明なら何もしない。枠だけを透かす設定なら、手間は枠の帯の分だけである。求め方は次の段落で述べる。
3. 合成。ウインドウをワークエリアと、上、下、左、右の枠の帯の5つに分け、それぞれの不透明度で背後と混ぜる。枠だけを透かす設定のワークエリアは行単位のコピーである。角は1ドットを64点でサンプリングした被覆率で背後と混ぜるので、輪郭が階段状にならない。ポインタの位置からウインドウを探すときは、被覆率が半分以上のドットからなる形を使う。辺に沿って走る線は、角を切る円と同じ中心で1ドットずつ内側の円に沿って描き直すので、枠は角で切り取られたようには見えず、角に沿って曲がる。描き直す深さは角の辺ごとに決める。スクロールバーのない辺では、枠の帯だけでなく、その内側に沿って描かれたもの(パネルがワークエリアの周りに描く太い枠など)も含めて角の範囲すべてを曲げる。スクロールバーのある辺と、タイトルバーのある上の辺では、外側の輪郭線とその内側の線の2本だけを曲げる(バーとタイトルの帯は線ではなく、帯にはピクトグラムがある)。それぞれの線の色は、角のすぐ外の2つの辺(縦の辺と横の辺)の画素から読み、角の中の各サンプルはより近い方の辺の線を取る。この描き直しはウインドウ自身の画素に対して組み立てのたびに行い、描き直しても結果が変わらないので、プログラムが角の中に描いたものも直り、GPUとCPUのどちらの合成も同じ画素を読む。
4. 色。枠の帯とタイトルバーに重ねる色は、合成の直前に掛ける。ウインドウのピクセルには描き込まないので、色を変えても枠を描き直す必要はなく、ウインドウを動かした跡にも色が残らない。

ぼかしは、縦横を半分ずつにした画像の段(レベル)を通して求める。レベル0は画面そのもので、レベルkの画素(x, y)は画面の(x×2^k, y×2^k)から2^k×2^kドットの範囲に当たる。この対応は組み立てる範囲によらず画面の位置で決まるので、ある画素の値は画面をどう分けて組み立てても同じになる。透ける部分ごとに、次の縮小を深さdの回数だけ行ってレベルdまで下り、レベルdで平滑化し、拡大をd回行ってレベル0に戻る。

| 処理 | 内容 |
| --- | --- |
| 縮小 | レベルkの画素を、レベルk−1の対応する位置の周りの4×4画素から、縦横それぞれ1、3、3、1の重み(合計64)で求める |
| 平滑化 | レベルdの画素を、同じレベルの周りの5×5画素から、縦横それぞれa、b、m、b、aの重み(各合計64)で求める。aが0なら3×3画素である |
| 拡大 | レベルk−1の画素を、レベルkのうち自分の中心に近い2×2画素から、近い方を3、遠い方を1の重み(縦横それぞれ合計4)で求める |

各処理はチャネルごとの重み付きの和を一度だけ丸めて8ビットに戻す。どの画素も1つ前のレベルの数画素だけから決まるので、GPUでは1画素を1つのフラグメントで求めて並列に処理でき、CPUと同じ値になる(13.10)。読む画素は、そのレベルのうち組み立てる範囲に掛かる画素に限り、その外は端の画素を繰り返す。CPUでは各処理を行方向と列方向に分けて行い、3つのチャネルを64ビットのワードの21ビットずつの区画に入れて同時に足す。最も大きい和(4096×255)でも区画からあふれない。

設定値rは、半径rの箱型の平均(2r+1画素の平均)と同じ広がり、すなわち方向ごとの分散r(r+1)/3(画素の2乗)になるように、深さと平滑化の重みに対応させる。縮小と拡大をd回ずつ行うと分散は(4^d−1)/2になり、レベルdの平滑化は自身の重みの分散の4^d倍を加える。深さは、縮小と拡大だけの分散がr(r+1)/3を超えない最も深いものとし、残りを平滑化で補う。平滑化の重みは64分の1単位で、中央が隣より小さくならないように選ぶ。どのrでも、求めた分散は目標と0.9以内で一致する。重みは中心が重く裾が滑らかに減るので、同じ分散の箱型の平均よりも輪郭がやや締まって見えるが、縞やブロック状の跡は出ない。

届く距離は、ある画素のぼかしが読む画面の画素までの最大の距離で、縮小と拡大の3(2^d−1)ドットに、平滑化の片側の画素数(aが0でなければ2、そうでなければ1)の2^d倍を加えたものである(`cp_spread_reach`)。CPUの手間は、ホストでの計測で、600×400のウインドウの枠だけをぼかすときr=2〜6で箱型の平均の0.7〜1倍、420×300のウインドウ全体をぼかすときr=2〜16で0.6倍前後である。枠の細い帯は周りのレベルの画素を余分に求めるので、r=16の枠だけのぼかしは箱型の平均の約1.5倍になる。

ぼかしは、組み立てる矩形の外側の画素も使う。一部の矩形だけを組み立てるときに透けてぼかすウインドウがその近くにあれば、届く距離にそうしたウインドウの数を掛けた幅だけ広い範囲を背景から組み立て、広げた縁の部分は組み立てる前の内容に戻す。数を掛けるのは、手前のウインドウがぼかすのは奥のウインドウがぼかした結果で、その分だけ遠くの画素に依存するからである。数えるのは広げた範囲の近くにあるウインドウで、広げると数が増えることがあるので、数が変わらなくなるまで繰り返す。逆に、ある部分の内容が変わると、その上で透けてぼかすウインドウでは、変わった部分から同じ幅だけ離れた画素まで見え方が変わる。そこで`wm_update`は、ウインドウの損傷と変わった場所を、同じ求め方の幅だけ広げてから部分として集める。こうすると、一部を組み立てた結果と画面全体を組み立てた結果が一致する。ぼかしを使わないとき(`LK_BLUR`が0、既定)は広げない。

手前のウインドウが奥のウインドウを影ごと覆うときは、奥のウインドウを重ねない。覆っているとみなすのは手前のウインドウの不透明な部分だけで、枠を透かすならワークエリア、角を丸めるなら角の行を除いた範囲である。ウインドウを開閉、移動、前面と背面の入れ替え、表示と非表示の切り替えをしたときは、影の届く範囲まで組み立て直す。

一部だけが覆われているウインドウも、見えている所だけを処理する(`cp_lay`)。手前のウインドウが不透明に描く画素は、そのウインドウの画素(重ねる色を掛けたもの)だけで決まり、背後の値によらない。そこへ奥のウインドウが落とした影や混ぜた画素は、手前のウインドウを重ねたときに消えるので、初めから処理しなくてよい。ほかの画素を読むのはぼかしだけで、ぼかしはそれまでに重ねた背景と奥のウインドウを読む。そこで、ぼかしが読む画素だけは、手前に不透明なウインドウがあっても奥のウインドウを重ねておく。

部分を組み立てるとき、最初のポップアップより奥のウインドウの並び(最大64個、超えた分は最も奥から従来どおりに重ねる)を手前から順に調べ、不透明に描かれる範囲を矩形の集まりとして集めていく。

1. ウインドウが届く範囲(外形、影、5つの部分)からこの集まりを切り取った残りが、そのウインドウの見えている所である。残りは最大16個の矩形で、それを超える切り取りは行わない。
2. 見えている所のうち透ける部分をぼかすなら、その部分を届く距離だけ広げた範囲を集まりから取り除く。そのウインドウの影は、見えている所に加えてこの範囲にも落とす。ぼかしが自分の影を落とした画素を読むためである。
3. そのウインドウが不透明に描く範囲を集まりに加え、2.の範囲をもう一度取り除いてから、奥のウインドウへ進む。不透明に描く範囲は、不透明度が255で透過色を使わない部分(全体が不透明なら外形)から、角を丸めるときの四隅の正方形を除いたものである。角の行のうち両端の角の間は不透明である。開閉の動きの途中のウインドウと独自の外形を持つウインドウは、不透明に描く範囲を持たない。

集まりは最大64個の矩形で、あふれたときは小さい矩形から捨てる。矩形を捨てたり切り取りを省いたりしても、処理する範囲が広がるだけで結果は変わらない。そのあと奥から順に、各ウインドウの影、ぼかし、合成を見えている所の矩形の中だけで行う。1つのウインドウでは、すべての矩形に影を落としてからぼかしをすべて求め、そのあとで合成する。ぼかしの各段は、矩形の中でも部分全体を読める範囲として求めるので、ある画素の値は矩形の分け方によらない。こうすると、ぼかしが読む画素は奥から順にすべてを重ねたとき(`cp_window`を並びの順に呼ぶ)と同じ値を持ち、組み立てた画面は画素ごとに一致する。GPUの起動時の確認(13.10.6)は`cp_window`を順に呼んだCPUの結果と比べるので、確認の基準も変わらない。GPUの実装は、1つのジョブの中で後のコピーが書き直す所を描かない(13.10.5)。CPUの実装も同じ考え方であるが、ぼかしが読む範囲だけを除くので、ぼかしのところで区切らずにウインドウの並び全体で隠れた所を省く。

QEMU(TCG、4コア、1280×800)で、ずらして重ねたウインドウを組み立てた時間は次のとおりである(カーネル試験の`test_hide_same`と`test_hide_time`、NEONの処理、ミリ秒)。

| 場面 | 従来 | 見えている所だけ |
| --- | --- | --- |
| 段階だけ、640×420の8個、不透明で角なし | 6.4 | 4.3 |
| 段階だけ、同じ8個、枠を透かし角を丸め影とぼかし | 27.5 | 19.2 |
| 段階だけ、同じ8個、全体を透かし角を丸め影とぼかし | 104 | 104〜109 |
| 合成タスクの画面全体、6個、不透明で角なし | 6.7 | 5.1 |
| 合成タスクの画面全体、6個、枠を透かし角を丸め影とぼかし | 23.6 | 16.8 |
| 合成タスクの画面全体、6個、全体を透かし角を丸め影とぼかし | 76.2 | 74.7 |

全体を透かすときは不透明な所がないので省けるものがなく、手間は従来と同じである。段階だけを測ると0〜5%遅く、合成タスクで測ると速いことも遅いこともある。従来の処理で枠を透かす8個の場面を段階ごとに測ると、背景のコピー1.1、影7.0、ぼかし11.7、合成8.1ミリ秒で、省いたのは隠れたウインドウの影とぼかしと合成である。`cp_hide_use`で省くのを止めると従来の処理になり、`cp_hidden`は省いた画素数を数える。

開閉の動きでは、開くウインドウを外形の236/256の大きさと72/255の濃さから元の大きさと濃さへ、閉じるウインドウをその逆へ、指定の時間で変化させる。進み具合は時刻から求めるので、処理が遅れても動きの時間は延びず、途中の段階が省かれる。閉じたウインドウはピクセルだけを残して動きが終わるまで重ね、終わったら解放する。動きの間は、ウインドウマネージャのタスク(優先度21)が、動いているウインドウの範囲の組み立てを16ミリ秒ごとに合成タスクに頼む(10.4.4)。組み立てを待たないので、動きの途中の段階は合成タスクが組み立てるたびにまとめて進む。

設定はデバイス設定の実身(`SYSDEF_CONF_DEV`)のレコード1に、`WIN_LOOK`、`WIN_OPACITY`などの行(`cf_look_items`)として保存する。`LK_GPU`の行は`WIN_GPU`である。起動時と、その実身が書き換えられたときに監視タスクが読み直して反映する。プロセスが`wm_set_look`でこれらの番号を書くと、範囲を確かめてからすべてのウインドウに反映し、画面を組み立て直す。

### 10.4.2 合成の実装

合成の段階には2つの実装がある。どのマシンでも使えるのはCPUによる実装(`compose.c`)で、QEMUとRaspberry Pi 4は常にこれで合成する。CPUの実装は、合成タスクの中ではNEONの命令で内側のループを処理する(10.4.4)。Raspberry Pi 5では、`V3D=2`または`V3D=3`でビルドしたとき、V3DのドライバがGPUによる実装を`cp_gpu_set`で登録する(13.10)。登録のインタフェース(`T_CPGPU`)は次の4つである。

| 項目 | 内容 |
| --- | --- |
| `align` | GPUが組み立てる範囲の左端の単位(ピクセル)。V3Dでは16(64バイト) |
| `wants` | その大きさの範囲をGPUで組み立てる価値があるか。起動時の確認(13.10.6)に通っていなければ常に偽 |
| `lay` | 背景と、奥から数えたウインドウの並び(`T_CPWIN`、最大64個)を受け取り、背景と並びの先頭から何個のウインドウを重ねたかを返す。失敗したら負の値を返し、何も重ねていないものとして扱う |
| `note` | 1回の組み立てにかかった時間を通知する。GPUの側が、GPUの組立ての時間の内訳(13.10.7)とあわせて統計としてコンソールに出す |

組み立てる部分が複数あるときは、部分ごとに次の判断をする。大きな部分はGPUで、小さな部分はCPUで組み立てることがある。`LK_GPU`が1で、登録された実装があり、その部分について`wants`が真のとき、部分の左端を`align`の倍数に、右端を倍数か画面の右端に広げる。広げた範囲も画面全体を組み立てたときと同じ内容になるので、広げた分も画面に送ってよい。次に、奥から順にウインドウを調べ(覆われていて重ねないものは除く)、最初のポップアップ(メニューや一覧)の手前までを`lay`に渡す。GPUが背景とその先頭からn個を重ねたら、CPUはn+1個目から後(メッセージ行、ポップアップ、閉じつつあるウインドウ、ドラッグ中の枠線を含む)をこれまでどおりに重ねる。このとき最初のポップアップまでのウインドウは、GPUの結果の上で見えている所だけを処理する(10.4.1)。ポインタはすべての部分を組み立てたあとで置く(10.4.3)。`lay`が失敗したときは、背景からすべてをCPUで組み立てる。GPUが重ねないウインドウ(独自の外形を持つもの)があれば、そこから後はCPUが重ねる。`lay`に渡した範囲のバックバッファの内容は、それまでCPUのキャッシュにあって書き戻していない値も含めて捨てられる(GPUが範囲のすべてのピクセルを書き直すため、13.10.5)。V3Dの実装は、範囲のうちどのウインドウもかからない所の背景を、GPUが働く間に`lay`の中でCPUがコピーすることがある。`lay`が返ったときの範囲の内容は、どちらが組み立てても同じである。範囲のうち後で元に戻す部分(ぼかしのために広げた縁、`cp_margin_keep`)は、`lay`の前に読んで取っておく。

小さな範囲(キャレットの点滅など)はCPUのほうが速い。`wants`は、起動時の確認で測った、GPUがCPUより速くなる範囲の大きさ(画素数)を閾値にし、見た目の効果を使うかどうかで2つの閾値を使い分ける。`note`は部分ごとに呼ぶ。

`wm_stat`は、組み立てた回数、重ねたウインドウと省いたウインドウの数に加えて、組み立てた部分の数、組み立てた画素数(ぼかしのために広げた縁を含む)、ポインタを新しい場所に置いた回数と、そのうち何かを組み立てたときの回数を返す。ウインドウマネージャは、組み立てか移動があった間、60秒ごとに次の形の1行をコンソールに出す。組み立てた画素数と送った画素数は1秒あたりの値も出す。Hは、手前の不透明なウインドウに隠れていて処理を省いたウインドウの画素数(千画素単位、10.4.1の`cp_hidden`の増分)で、同じ画素を複数のウインドウの分だけ数えるので、組み立てた画素数を超えることがある。末尾は画面ドライバの送りで、送りの回数Dと1回あたりの時間(マイクロ秒)、面を切り替えた回数F、切り替えが効くのを待った回数Wと1回あたりの時間(10.2.1)である。1面の画面ではFとWは0になる。

```
wm: in T s: B builds (P parts), X kpx built, X/T kpx/s, H kpx of windows hidden and left out; R rects sent, S kpx, S/T kpx/s; pointer moved M times, N with something built; D sends of U us each, F flips, W waited for a flip, V us each
```

### 10.4.3 ポインタ

ポインタは、組み立てた画面の上にバックバッファへ直接置き、置く前にその正方形の下にあった画素を取っておく(`pointer.c`)。ポインタだけが動いたときは、取っておいた画素を元の場所に戻し、新しい場所の画素を取ってからポインタを置き、その2つの正方形だけを画面に送る。ウインドウは1つも組み立て直さない。どのウインドウマネージャの組み立ても、組み立てる部分(ぼかしのために広げた縁を含む)がポインタの正方形にかかるときは、先にポインタを取り除いて下の画素を戻し、部分を組み立て、最後に新しい下の画素を取ってからポインタを置き直す。こうすると、取っておく画素は常にその場所のウインドウの見え方(ドラッグ中の枠線を含む)と一致し、バックバッファを読む試験やスクリーンショットには、画面全体を組み立てたときと同じ画面が見える。ポインタの形(`wm_set_pointer`)や大きさ(`LK_PTR_SIZE`)が変わったとき、表示を消したとき(`wm_show_pointer`)も、次の`wm_update`か`wm_pointer_moved`で同じように取り除いて置き直す。ポインタを置く場所は、その時点で入力層が返す位置(`ts_hid_pointer`)である。入力層はポインタの移動を受け取るたびに合成タスクを起こし(`knl_wm_pointer_hint`)、合成タスクは次の組み立てでポインタをその時点の位置に置く。ポインタを動かすのはイベントを読むプログラムではないので、デスクトップが重い処理をしている間もポインタはマウスに従う。`wm_pointer_moved`も組み立てを頼むだけで、待たずに戻る。`wm_pointer_last`は最後に置いた正方形の左上と大きさを返し、まだ一度も置いていなければ偽を返す(このとき`wm_update`は画面全体を組み立てる)。画面の解像度が変わったときは、取っておいた画素を捨ててから画面全体を組み立てる。

Raspberry Piのファームウェアには、メールボックスのプロパティでハードウェアカーソルを使うタグ(0x00008010で形とホットスポット、0x00008011で表示と位置)がある。文書にある条件は32ビットARGBの画像をVideoCoreのバスアドレスで渡すことで、どの機種とどの表示経路で働くかは書かれていない。Pi 5のファームウェアが用意するフレームバッファで働くかは確かめていないので、使っていない。

### 10.4.4 合成タスク

画面を組み立てるのは、ウインドウマネージャの合成タスク(優先度10)だけである。入力(USBの管理タスク、優先度8)とGPU(優先度9)より低く、デスクトップやプロセスのタスクより高い。`wm_composite`、`wm_composite_at`、`wm_update`、`wm_set_drag`を呼んだタスクは自分では組み立てず、何を組み立ててほしいか(画面全体、矩形、変化した所)を記録して合成タスクを起こし、その組み立てが終わるまで待つ。組み立ては1更新に1回までである。2面を切り替え、切り替えが効いたことが画面から分かる(帰線を待てるか、効くまでの時間が決まっている)ときは、組み立てた画面の送りが前の切り替えが効くのを待つので(10.2.1)、その待ちが画面の更新に合わせて1更新に1回に揃える。`ts_disp_paced`はそのときの更新の周期を返し、合成タスクは自分では待たずに、依頼が来ればすぐに組み立てる。合成タスクも間隔を取って待つと、自分の待ちの後に送りの待ちが重なり、その間に帰線を1回逃して、1フレームを2更新続けて表示することがある。それ以外の画面では、組み立てを始める時刻を`WM_FRAME_US`(16667マイクロ秒、60Hzの1フレーム)おきの位置に合わせる。次の位置は前回の組み立てを始めた時刻ではなく前回の位置から数え、マイクロ秒の単位で眠る(`tk_dly_tsk_u`)。前回の開始から数えて残りをミリ秒に切り上げて眠っていたときは、ウインドウに描いては`wm_update`することを続けても、QEMUで組み立ての間隔が17.6ミリ秒(毎秒56.8回)になり、疑似的な更新で2面を切り替えても同じだった(`test_pace`)。今は16.66ミリ秒である。位置に遅れて始めたときも次は次の位置で始めるが、前回の開始から半フレームは空ける。1フレームより長く依頼がなかったときは、依頼が来ればすぐに組み立て、そこから位置を数え直す。待つ間に届いた依頼は、次の1回の組み立てにまとめる。1フレームのうちに10回変化しても、組み立ては1回である。

変化した所は、依頼を受けた時ではなく組み立てを始める時に集める。ウインドウの損傷(`wm_damage`)、ウインドウの開閉や移動などで変わった場所(`wm_gone`)、ウインドウの描画環境で描いた矩形(10.2)である。描いた矩形はタスクごとに分けて持ち、そのタスクが組み立てを依頼したときに初めて組み立ての対象にする。ほかのタスクの依頼やポインタの移動による組み立てで、描いている途中のウインドウ(ページを塗りつぶして文字をまだ描いていない状態)が画面に出ないようにするためである。

| 関数 | 動作 |
| --- | --- |
| `wm_composite` | 画面全体の組み立てを依頼し、終わるまで待つ。外観、配色、壁紙、解像度のように画面全体が変わるときに使う |
| `wm_composite_at` | 矩形の組み立てを依頼し、終わるまで待つ |
| `wm_update` | 変化した所の組み立てを依頼し、終わるまで待つ |
| `wm_post` | `wm_update`と同じ依頼をして、待たずに戻る。すぐに描き直さない呼び出し元(開閉の動きのタスク)が使う |
| `wm_flush` | それまでにどのタスクが依頼した組み立ても終わるまで待つ |
| `wm_pointer_moved` | 組み立てを依頼して待たずに戻る。ポインタは組み立てのたびにその時点の位置に置く |

待つのは、続けて描き直す呼び出し元の描きかけを合成タスクが読まないようにするためと、試験が戻った直後のバックバッファを読めるようにするためである。待つ呼び出し元はそれぞれセマフォ(16個)で待ち、合成タスクは組み立てを終えると、その組み立てで済んだ依頼の待ち手だけを起こす。16個を超えたときは1ミリ秒ごとに確かめる。合成タスクがない間(起動の途中と、作れなかったとき)と、合成タスク自身が呼んだときは、呼び出し元がその場で組み立てる。ロックは、ウインドウマネージャのロック(`wm_mtxid`)、描いた矩形を守るロックの順に取る。描いた矩形のロックは最後に取るロックで、描画管理から呼ぶときは描画管理のロックを持っていない。組み立ての間は、これまでどおりウインドウマネージャのロックと画面の保留(`ts_disp_hold`)を持ち、GPUで組み立てるときはGPUの処理が終わるまで合成タスクが待つ。

デスクトップは、キャレットや選択枠の点滅、ウインドウのドラッグ中の移動、メニュー、パネル、ツールのウインドウ、ダイアログのような部分的な変化に`wm_update`を使い、`wm_composite`は起動と終了、解像度の変更、試験からの外観の変更だけで使う。キャレットの点滅では、ウインドウの描画環境の表示範囲をキャレットの矩形に絞ってページを描き直すので、画面に送るのもキャレットの矩形だけである。スクロールバーは、値が変わらなければ描き直さない(`wm_set_bar`)。

合成タスクは`TA_FPU`で生成するので、浮動小数点とSIMDのレジスタを持つ(4.2)。CPUの合成の内側のループは、合成タスクの中ではNEONの命令(`outer_kernel/wm/compose_simd.c`)で処理する。行のコピー(背景、不透明な行、ぼかしのために広げた縁の保存と復元)、不透明度による混合、枠とタイトルバーに重ねる色、プログラムの色、角の行のうち被覆率が255の中央、影の濃さ(濃さの計算は従来どおり1画素ずつ行い、暗くするところだけを4画素ずつ行う)、ぼかしの縮小、平滑化、拡大である。混合の255での割り算は、v+1+(v>>8)を8ビット右に送る計算で、v<65535で正確に一致する(混合の最大は255×255+127)。ぼかしの和は1チャネルを16ビットの区画に入れ、平滑化の列方向だけ32ビットで足す。どの処理も従来のCPUの処理と同じ画素を書く。`compose.c`は、そのタスクがNEONを使えると登録されているか(`cp_simd_allow`)を部分ごと、行ごとに確かめ、ほかのタスク(GPUの起動時の確認など)から呼ばれたときは従来の処理を使う。`compose_simd.c`だけは`-mgeneral-regs-only`と`-mstrict-align`を外してビルドする。`-mstrict-align`のままでは16バイトのロードとストアが4バイトずつに分けられる。扱うのはどれも通常のメモリで、整列の検査(`SCTLR_EL1.A`)はしていない。フレームバッファへの転送はデバイスのメモリへの書込みで整列が要るので、画面ドライバの従来のコピーのままにしてある。

カーネル試験の`wm`の組には、20回の依頼が1〜2回の組み立てにまとまること(`test_coalesce`)、描画環境で描いただけの部分が次の`wm_update`で画面に出ること、入力層だけでポインタが動くこと、乱数で作った100の場面(ウインドウ1〜4個、不透明度、角の丸み、影、ぼかし、色、透過色、組み立てる範囲を変える)でNEONと従来の処理の結果が1画素も違わないこと(`test_simd_same`)、画面全体を両方で組み立てて同じになること(`test_simd_time`)を確かめる試験がある。見えている所だけを処理すること(10.4.1)については、乱数で作った200の場面(ウインドウ2〜12個、多くは全体か枠が不透明、一部は開閉の途中、NEONと従来の処理を交互に、組み立てる範囲を変える)で、`cp_lay`の結果が`cp_window`を順に呼んだ結果と1画素も違わず、省いた画素があること(`test_hide_same`)、画面の大きさで8個のウインドウを3つの見た目で組み立てて両方が同じになること、合成タスクで6個のウインドウを画面全体について両方で組み立てて同じになること(`test_hide_time`)を確かめ、それぞれの時間を出す。

QEMU(TCG、4コア、1280×800)でデスクトップを操作して測った値は次のとおりである(`tools/ui_run.py`の`stat`と`lag`。組み立てた画素数は千画素単位)。

| 操作 | 変更前 | 変更後 |
| --- | --- | --- |
| 何もしない5秒 | 6回、6144 | 6回、1未満 |
| 文書を開いてキャレットが点滅する5秒 | 7回、6145 | 6〜7回、1未満 |
| キャレットの点滅中に4秒ポインタを動かしたときの最大の遅れ | 38ミリ秒 | 6ミリ秒 |
| 同じ間の組み立て | 5回、5120 | 4回、1未満 |
| 10文字の入力(落ち着くまで) | 30回、24725 | 20回、5607 |
| ウインドウのドラッグ(12段階) | 12回、12288 | 11〜12回、5778 |

TCGはNEONの命令を1命令ずつ補助関数で模擬するので、QEMUではNEONの処理は従来の処理と同じ程度の速さで(画面全体の組み立ての段階だけで、不透明で角のない3つのウインドウが1.4ミリ秒対1.1ミリ秒、見た目の効果を全部使うと37ミリ秒対43ミリ秒)、差は測れない。実機の速さは`test_simd_time`と`test_simd_same`が出す値で確かめる。

### 10.4.5 フレームの歩調の測定

アニメーションのように続けて描くプログラムが毎秒60フレームに届かないとき、どこで1フレームを越えたかを、合成タスク、画面ドライバ、プログラムの3か所で数える。

ウインドウマネージャは`wm_frames`(`T_WMFRAMES`)で、組み立ての回数、続けて始めた組み立て(前の開始から`WM_APART_MS`(100ミリ秒)以内)の間隔の合計と最大、そのうち更新1.5回分より間が空いた回数、ウインドウを重ねるのにかかった時間(合計と最大)、組み立てた画面の送りにかかった時間(前の切り替えが効くのを待つ時間を含む)、間隔を取るために眠った時間、組み立てを待った呼び出し元(`wm_update`など。プログラムがフレームを出す`wm_obj_put`もこれで待つ)の回数と時間を数える。画面ドライバは`ts_disp_frames`(`T_DISPFRAME`)で、更新の周期、切り替えの回数、切り替えの間が更新何回分だったか(四捨五入して、半分未満、1、2、3、4以上)、帰線の時計があるときに切り替えが帰線の終わりから更新のどの4分の1で行われたか、前の切り替えが効いたかを確かめた送りの数、そのうち時計で効いたと分かって待たなかった数、画面を見て帰線を待った数、見て待った時間と眠った時間、時計から外れた帰線の数を数える。

組み立てが毎秒20回以上続く間は、10秒ごとに次の2行をコンソールに出す(`WM_FRAMES_MS`、`WM_FRAMES_MIN`)。Raspberry Pi 5ではCOM3に出る。数値は例である。

```text
wm: frames: in 10000 ms 600 builds, 60.0 a second; 16666 us apart (most 17200), 0 over a refresh and a half; laying 900 us (most 2100), sending 13800 us (most 16500), asleep for the pace 0 us, a build each; 600 waits for a build, 14500 us (most 16900)
disp: frames: refresh 16667 us; 600 flips, refreshes apart 0:0 1:600 2:0 3:0 4+:0; quarter after the blank 598/2/0/0; 600 sends during a flip: 0 taken by the clock, 600 waited (watching 1100 us, asleep 11500 us each), 0 blanks off the clock
```

小物「歯車」は、5秒ごとの行に、1フレームを描く呼び出し(GPUの仕事を積むだけの部分)の時間と、`eglSwapBuffers`の時間(GPUの仕事の終わりを待ち、ウインドウの画素へコピーし、その画面が組み立てられて送られるまで待つ)の平均と最大を加える。

```text
glgears: 300 frames in 5.0 seconds = 60.0 fps (320x280); drawing 400 us (most 900), eglSwapBuffers 16000 us (most 17000) a frame
```

読み方は次のとおりである。

| 見る所 | 分かること |
| --- | --- |
| `disp: frames:`の`refreshes apart`が1以外に多い | 2なら切り替えが1回の帰線を逃した。0なら1更新に2回切り替えている(帰線を待てていない) |
| `taken by the clock`が多い | 送りが前の帰線の後に来た。時計がなければ、その分だけ更新1回分を余計に待っていた |
| `blanks off the clock`が0でない | 帰線の時計が外れている。`hvs: clock:`の行の周期と帰線の長さを見る |
| `quarter after the blank`が後ろの4分の1に寄る | 送りが帰線の直前に終わっている。重ねる時間かコピーする時間を減らす余地がある |
| `wm: frames:`の`apart`が更新より長く、`asleep for the pace`が0 | 組み立てが依頼を待っている。プログラムのフレームが遅い |
| `sending`が長く`watching`と`asleep`の和に近い | 送りの時間のほとんどは前の切り替えが効くのを待つ時間で、待つ相手は画面の更新である |
| `glgears:`の`eglSwapBuffers`から`wm: frames:`の`waits for a build`の時間を引いた残り | GPUの仕事の終わりを待つ時間とウインドウの画素へコピーする時間 |
| `glgears:`の`drawing`と`eglSwapBuffers`の和が更新より長い | プログラムのフレームが1更新に収まっていない。合成や送りではなくプログラムかGPUの側を見る |

カーネル試験の`disp`の組の`test_blank`は、疑似的な更新(16667マイクロ秒)で、切り替えの直後の送りがその切り替えを取る帰線の終わりまで待ってそれ以上は待たず、その切り替えが更新の最初の4分の1に入ること、切り替えから17.8ミリ秒後(帰線の後で、効いたとみなす時間の内)の送りが待たずに時計で効いたと分かること、30回続けた送りが更新1回分ずつ間を空け、帰線の前に眠ること、時計が外れないことを確かめる。`wm`の組の`test_pace`は、ウインドウに描いては`wm_update`することを60回繰り返し、1面で送る画面では合成タスクが16667マイクロ秒おきの位置で組み立て、60フレームが1秒(60×16667マイクロ秒)と30ミリ秒の内に収まること、疑似的な更新で2面を切り替える画面では合成タスクが眠らず、切り替えが1更新に1回(更新1回分の間)になることを確かめる。

## 10.5 外観設定テーブル

ウインドウ、部品、パネル、メニューの色、パターン、長さ、時間は、番号付きの外観設定テーブルから取得する。番号は固定で、定義は番号でテーブルの値を参照する。

| 番号 | 内容 |
| --- | --- |
| 250〜319 | 長さと時間(タイトルバーの高さ、スクロールバーの幅、ダブルクリックの間隔、カーソルの点滅) |
| 400〜499 | パターン(背景、縁、タイトルバー、ランプ、スクロールバーのつまみ) |
| 550〜579 | 色 |
| 580〜599 | フォント |
| 9000〜9199 | 設定(ウインドウの見た目、キーとポインタの属性、音、入力方式) |

配色は外観設定テーブルの値の組で、システム環境設定で切り替える。ウインドウの見た目(10.4.1)とユーザ環境設定で変更する値も、このテーブルの設定項目である。タイトルの文字サイズとスクロールバーの幅を変えると、開いているすべてのウインドウの枠とワークエリアがその場で再計算され、再描画される。メニューの文字サイズは次に開くメニューから反映される。ポインタのサイズを変えたときは、変更前のサイズで覆っていた画素を戻し、新しいサイズで置き直す。プロセスは`wm_look`で値を読み出し、管理者は`wm_set_look`で書き換えられる。

## 10.6 部品

部品は、BTRONの部品と同じ種類と番号を持つ。

| 番号 | 部品 |
| --- | --- |
| 1 TB | テキストボックス |
| 2 XB | 秘匿テキストボックス(パスワード入力) |
| 3 NB | 数値ボックス |
| 4 SB | 連番ボックス(数値や名前の欄を並べたもの) |
| 5 AS | オン/オフスイッチ |
| 6 MS | 押しボタン |
| 9 WS | スイッチセレクタ |
| 10 SS | スクロールセレクタ |
| 11 VL | ボリューム |
| 13 | タブパネル |
| 0 | ラベル |
| 14 | 線 |
| 15 | アイコン |
| 16 | ポップアップ |

部品の描画と操作は次のとおりである。

- 名前の文字は16ドットで、明るい色の影を右下に1ドットずらして付ける。
- スイッチは角を丸めた立体的な箱で、Enterで押されるスイッチは内側に強調枠を持つ。
- オン/オフスイッチとセレクタの名前の前にはランプがあり、選択したものが点灯する。現在有効な値の名前には下線を引く。
- 押しボタンにランプはない。名前の文字間を広げてボタン全体に描き、押している間は枠を反転表示する。
- スイッチとセレクタは、ボタンを離したときに部品の上にあれば有効になる。押したまま部品の外へ出ればキャンセルできる。
- テキストボックスは、入力フォーカスを持つ間は白背景になり、カーソルが点滅する。Tabで次のボックスに移り、ボックスに入ると文字列全体が選択される。かな漢字変換で日本語を入力できるボックスもある。
- 連番ボックスは欄ごとに数値か名前を持つ。入力中の欄の下の三角を押すか、上下の矢印キーで値が増減する。
- ボリュームはスクロールバーと同じ形で、つまみをドラッグして値を変える。
- ポップアップは、いくつかの名前から1つを選ぶ部品である。押すと名前の一覧が開き、選んだ名前が部品に出る(下記)。

タブパネルは、上下2段のタブを持つ部品である。各部品は自分が属するタブを持ち、そのタブが選択されているときだけ描画され、操作を受け付ける。タブはふつうシートの上に横に並ぶ。`P_DOWN`を指定すると、シートの左側に縦に並ぶ。縦に並べたタブは横のタブを横倒しにした形で、幅はいちばん長い名前に合わせてそろえ、下の段は持たない。選択できないタブは灰色の名前で描き、押しても選ばれない(`inact`)。トレー小物(11.27)が使う。

ポップアップ(`WM_PT_POPUP`、16)は、セレクタと同じく名前の並びを持ち、値は選んでいる名前の番号(1から、0は選んでいない)である。名前の並びはパネルの名前の置き場にセレクタと同じ形で置き、プロセスは部品のレコード4に書いて入れ替える。デスクトップのようにカーネルの中でパネルの定義(`T_WMPANEL`)を作るときは、部品の`type`を`WM_PT_POPUP`にし、`wm_panel_name`で名前を置き場に入れて最初の名前の位置を`pool`に、名前の数を`count`に、選んでいる番号を`value`に書く。開いたあとの値は`wm_panel_get`と`wm_panel_set`で読み書きする。BTRONの部品の番号7と8は絵を持つスイッチと押しボタンなので、ポップアップにはTessronOSが足した部品の番号の続きを使う。

見た目は次のとおりである。

- 本体はスイッチと同じ角の丸い立体的な箱で、外観設定テーブルの部品の背景(`LK_INACTPARTS`)で塗る。`P_NOFRAME`なら枠を描かず背景だけ、`P_EMPHAS`ならスイッチと同じ強調枠を内側に描く。
- 選んでいる名前を、セレクタの名前と同じ位置(左端からマージン16ドット)に、ランプを付けずに描く。名前にタブがあれば、タブの後ろを印の手前に右寄せで描く。
- 右端のマージンと8ドットの幅の欄に、下向きの三角の印を描く。幅はマージンの3/4、高さは3/8で、ボリュームのつまみや連番ボックスの三角と同じパターン(`LK_PEMPHAS`)で塗る。
- 一覧が開いている間は、押しボタンを押している間と同じく枠を反転表示する。操作できない部品はスイッチと同じく白の網掛けで覆う。

一覧はメニューの一覧と同じもので、自分のポップアップウインドウとして、ほかのすべてのウインドウより前に開く。メニューの文字の大きさで名前を1行に1つ並べ、枠と網掛けの影を付け、ポインタの下の行を反転表示する。選んでいる名前の行には印を付ける。名前のタブの後ろは、メニューのキーの欄と同じく右端にそろえる。選べない名前(`inact`)は淡色で描き、選べない。一覧は、選んでいる名前の行が部品に重なり、名前の書き出しが部品の名前の書き出しとそろう位置に開く。幅は部品の幅以上である。画面からはみ出すときはメニューと同じく画面の中に寄せる。画面の高さに入りきらない数の名前があるときは、選んでいる名前を中心にした入るだけの行を出す。

操作は次のとおりである。

- 部品を左ボタンで押すと一覧が開く。押したまま行の上へ動かして離すと、その名前を選ぶ。
- 押してすぐ(ダブルクリックの間隔のうちに)開いたときの行の上で離すと、一覧は開いたままになる。そのあと行を押して離すと選ぶ。
- 一覧の外で離したとき、一覧の外を押したとき、Escのときは、何も変えずに一覧を閉じる。右ボタンでは選ばない。
- 上下の矢印キーで反転表示する行を動かし(選べない行は飛ばす)、Enterで選ぶ。
- 一覧が開いている間、ポインタとキーの入力は一覧だけに渡し、下のウインドウやパネル、プロセスには通知しない。入力を読む`wm_read_event`が、ほかへ渡す前に`knl_pn_list_event`に渡す。

名前を選ぶと部品の値が変わり、部品に離した通知(`OB_E_RELEASE`)と、値が変わったときは変化の通知(`OB_E_CHANGE`)が出る。`lib/libui`では`UI_EV_CHANGE`になり、`ui_value`で選んだ番号を読み、`ui_set_value`で選ぶ名前を変え、`ui_names`で名前の並びを入れ替える。パネルを閉じたとき、部品を無効か非表示にしたとき、名前の並びを入れ替えたときは、開いている一覧を閉じる。一覧は画面に同時に1つだけである。

## 10.7 パネルとデータボックス

パネルは部品を並べたものである。パネルの定義は、データボックス実身のレコード0に、番号付きの`<panel>`要素としてxmlTADで書く。

```xml
<databox>
<panel num="1" rect="0,0,435,324" title="ネットワーク設定" kind="bare">
<tags num="100" rect="0,0,435,324" inner="4,28,431,320" value="1">
<tag>＠ネットワーク</tag><tag>アドレス</tag><tag>＋状態</tag>
</tags>
<text sheet="1" x="8" y="80">自ホスト：</text>
<box num="11" sheet="1" rect="136,58,264,88" max="79" ascii="true"/>
<button num="35" sheet="2" rect="320,272,408,296">表示更新</button>
</panel>
</databox>
```

部品の要素には、`text`(ラベル)、`tags`(タブパネル)、`box`(テキストボックス)、`secret`(秘匿テキストボックス)、`number`(数値ボックス)、`serial`(連番ボックス)、`switch`(オン/オフスイッチ)、`button`(押しボタン)、`select`(セレクタ)、`list`(スクロールセレクタ)、`popup`(ポップアップ)、`volume`(ボリューム)、`line`(線)、`icon`(アイコン)がある。アイコンの部品(`WM_PT_ICON`)は、実身のアイコンを仮身と同じ絵で見せる。プログラムが実身のUUIDを文字として書く(テキストボックスと同じく状態のレコードに書く)と、カーネルはその時に書いたプログラムのタスクでアイコンを読み、描くときは覚えた絵を部品の矩形の中央に置く(大きければ縮める)。空の文字なら何も描かない。押しても何も起きない。設定の小物のウインドウ(`lib/libui`、`ui_open`)は、開く前に`ui_attr`で大きさを変えられることと右の縦のスクロールバーを頼めば、それを持つ。スクロールバーはウインドウの持ち主のもので、`ui_bar`で全体と見えている所を書き、つまみや溝の操作(`UI_EV_SCROLL`)、ホイール(`UI_EV_WHEEL`)、大きさの変化(`UI_EV_SIZE`、`ui_work`で作業領域の大きさを読む)を受けて、パネルに見せるものを替える。パネル自身は動かない。ラベルの位置は(x、ベースライン)で指定する。部品はプログラムから`num`の番号で指定する。

ポップアップは`<popup num="16" rect="120,282,440,308" value="1"><name>明朝</name><name>ゴシック</name></popup>`のように書く。`<name>`は省いてよく、そのときはプロセスが開いたあとで名前の並びを書く。`value`を省くと、名前があれば1、なければ0である。高さはテキストボックスと同じ26ドットほどにする。

プロセスは、パネルの実身を作成するときにメタデータの`tessronos.part`に`box`(データボックスのUUID)と`num`(パネルの番号)を指定し、`ob_map_rec`で自分のウインドウに配置する。パネルのリンクのレコードから部品のUUIDを取得し、部品を開く。部品の値は状態のレコード(3)で読み書きし、セレクタの名前の並びは部品のレコード4に書く。無効状態と非表示状態は配置のレコード(2)のフラグで切り替える。部品で起きたイベントはパネルのその部品のリンクのレコードにも通知されるので、パネルに一度だけ通知を要求すればよい。

`lib/libui`は、この手順と、部品を番号で読み書きする関数をまとめたライブラリである。描画は一切しない。

## 10.8 メニュー

メニューは定義実身から作成する。定義実身のレコード0の`<menu>`要素に項目を並べる。

```xml
<menu>
<include><link id="…_0.xtad"/></include>
<item code="update" key="S">設定を更新</item>
<line/>
<item code="clear">削除</item>
</menu>
```

`<include>`は別の定義の項目をその位置に取り込む。どのウインドウのメニューにも出る共通の項目(閉じる、仮身操作、実身操作、屑実身操作、ウインドウ、小物、実行)はシステムの定義実身にあり、プログラムはそれを取り込むだけでよい。項目にリンクを持たせると、そのリンク先の定義がその項目のサブメニューになる。プログラムのコードが扱うのは定義実身のUUIDと項目の`code`だけで、メニューの文言や並び順はコードに書かない。プロセスは`mn_cre_men`でメニューを作成し、`mn_pop_men`で表示して選択結果を受け取る。

## 10.9 メッセージ行とトレー

画面下端のメッセージ行は、入力モード(英字、日本語、ローマ字、かな)と時刻を表示し、プログラムの短いメッセージを表示する(`wm_msg_put`)。トレーは、プログラム間で仮身や文字列を受け渡すための一時的な保管場所(クリップボード)である。プロセスは`tr_`のSVC(付録Aのクラス9の20〜29)でトレーを使う。トレーはシステムの実身で、そのキーはカーネルのものなので、プロセスの呼出しはカーネルのタスクが1件ずつ代わりに行い、入れるバイト列と取り出すバイト列はカーネルのメモリを通して受け渡す。

## 10.10 かな漢字変換

かな漢字変換は、Mozcを移植した変換エンジン(`MOZC=1`でリンクする)で行う。リンクしない構成では、ローマ字からかなへの変換だけを行う。入力モードは[ひらがな/カタカナ]キーで日本語、[英数]キーで英字に切り替わる。デスクトップの文章と図形のウインドウ、パネルのテキストボックス、プロセス(`kc_`のSVC)が、同じ変換エンジンを使う。小物「単語登録」でユーザ辞書に登録した単語は、どちらの構成でも変換の候補に出る(11.16)。
